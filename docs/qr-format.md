# Формат QR-кодов YU Inventory

## Статус документа

Этот документ задаёт нормативный формат новых QR-кодов и правила распознавания уже нанесённых кодов для корпусов, кабинетов и предметов. Реализация генератора, единого реестра и resolver API должна следовать этим правилам.

## Основные инварианты

- QR-код идентифицирует объект, но не подтверждает право пользователя на действие.
- Тип объекта определяется только сервером после поиска в едином реестре QR-идентификаторов.
- Значение QR уникально глобально между корпусами, кабинетами и предметами.
- В QR не помещаются тип объекта, ID базы данных, инвентарный номер, локация или персональные данные.
- Отозванное значение никогда не выдаётся повторно: старая наклейка может продолжать существовать физически.
- Сканирование само по себе ничего не изменяет. Принятие, передача и результат проверки выполняются отдельными серверными командами.
- Сканирование предмета в другом кабинете не меняет его фактическую локацию.

## Канонический формат

Новый QR содержит текст:

```text
YUQ1:<TOKEN>
```

Где:

- `YUQ1:` — сигнатура и версия формата;
- `<TOKEN>` — 26 символов Crockford Base32;
- разрешённый алфавит токена: `0123456789ABCDEFGHJKMNPQRSTVWXYZ`;
- токен создаётся криптографически стойким генератором с энтропией не менее 128 бит;
- генерация не должна использовать последовательный ID, время, тип объекта или другие данные карточки.

Регулярное выражение полного payload:

```regex
^YUQ1:[0-9A-HJKMNP-TV-Z]{26}$
```

Пример:

```text
YUQ1:7K3M9W2T8R5D4H6N1P0QX9C2BZ
```

Префикс версии позволит добавить новый формат без переиздания существующих наклеек. Домен приложения намеренно не входит в payload, поэтому перенос системы на другой домен не ломает QR-коды.

## Канонизация ввода

Камера и ручной ввод используют один алгоритм и одинаково принимают:

- полный payload `YUQ1:<TOKEN>`;
- только 26-символьный `<TOKEN>`.

Обе формы преобразуются в один `canonical_key` вида `YUQ1:<TOKEN>`. Для системного формата внешние пробелы удаляются, после чего значение приводится к верхнему регистру. Символы `I`, `L`, `O` и `U` запрещены. Система не заменяет их автоматически на похожие цифры или буквы, а показывает ошибку формата.

Пространство системных идентификаторов зарезервировано:

- legacy alias не может состоять из 26 символов Crockford Base32 независимо от регистра;
- любое нормализованное значение, начинающееся с регистронезависимого ASCII-префикса `YUQ`, считается системным, а не legacy;
- неправильный `YUQ1:` возвращает `INVALID`;
- синтаксически корректный префикс `YUQ<цифры>:`, кроме `YUQ1:`, возвращает `UNSUPPORTED_VERSION`;
- любое другое значение с началом `YUQ` возвращает `INVALID` и не переходит в legacy-поиск;
- зарезервированное значение нельзя добавить через миграцию или ручную привязку.

Ручной ввод кода не отменяет авторизацию и не расширяет права пользователя.

## Единый реестр QR

QR нельзя хранить как три независимых уникальных поля в таблицах корпусов, кабинетов и предметов. Используется единый реестр со следующей логической моделью:

| Поле | Назначение |
| --- | --- |
| `original_value` | Исходное значение для отображения и аудита |
| `canonical_key` | Нормализованный глобально уникальный ключ |
| `format` | `generated_v1`, `legacy_raw` или `legacy_url` |
| `target_kind` | `building`, `room` или `item` |
| `target_id` | Идентификатор целевого объекта |
| `role` | `primary` или `alias` |
| `status` | `active` или `revoked` |
| `created_by`, `created_at` | Автор и время привязки |
| `revoked_by`, `revoked_at`, `revoke_reason` | Данные отзыва |

Обязательные ограничения:

- один объект имеет не более одного активного `primary`-кода;
- объект может иметь несколько активных legacy aliases;
- `canonical_key` уникален глобально, включая отозванные значения;
- legacy alias не пересекается с зарезервированным пространством системных идентификаторов;
- для каждого идентификатора заполнена ровно одна допустимая цель;
- замена primary-кода, отзыв старого кода и запись аудита выполняются одной транзакцией;
- старый отозванный код возвращает состояние «Код заменён или отозван», а не «Неизвестный код».

## Входной фильтр

Камера, ручной ввод, миграция и команды привязки используют одну функцию нормализации в строгом порядке:

1. Отклонить исходный payload длиннее 512 байт до декодирования.
2. Декодировать только корректный UTF-8 без замены ошибочных байтов.
3. Удалить ровно один `U+FEFF`, только если он является первым символом.
4. Удалить с обоих краёв только `U+0009` (TAB), `U+000A` (LF), `U+000D` (CR) и `U+0020` (SPACE).
5. Отклонить пустую строку и исчерпывающий набор placeholder-значений `-` и `??`.
6. Отклонить оставшиеся C0/C1 controls (`U+0000–U+001F`, `U+007F–U+009F`), `U+FEFF`, bidi controls (`U+061C`, `U+200E`, `U+200F`, `U+202A–U+202E`, `U+2066–U+2069`) и не-ASCII пробелы (`U+00A0`, `U+1680`, `U+2000–U+200A`, `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`).
7. Выполнить системную канонизацию либо сохранить legacy-строку без дальнейших преобразований.

Пробел `U+0020` внутри legacy-кода сохраняется. TAB, CR и LF допустимы только по краям и удаляются на шаге 4. Если перед BOM находится пробел либо BOM встречается повторно или внутри строки, значение отклоняется.

Resolver никогда не выполняет найденную строку как URL, HTML или команду и не отправляет запрос на содержащийся в ней адрес.

Для legacy-кодов сохраняются разделители, внутренние пробелы, регистр, ведущие нули и Unicode-символы. Не применяются NFKC, удаление внутренних пробелов и взаимозамена `/`, `-` или `\`.

## Порядок распознавания

Resolver выполняет шаги строго в следующем порядке:

1. Применяет входной фильтр.
2. Канонизирует полный `YUQ1:<TOKEN>` или голый токен одинаково для камеры и ручного ввода.
3. Если значение имеет зарезервированный системный префикс, проверяет версию и формат; системные значения никогда не переходят в legacy-поиск.
4. Ищет системный код точным поиском в едином реестре, включая активные и отозванные записи.
5. Для legacy-значения одновременно ищет точное совпадение во всём QR-реестре и среди текущих официальных инвентарных номеров.
6. Если найден отозванный QR-идентификатор, возвращает `REVOKED` до любых fallback-проверок.
7. Если кандидаты указывают на разные объекты или официальному номеру соответствуют несколько предметов, возвращает `AMBIGUOUS`.
8. Возвращает единственный активный объект без изменения данных.
9. Возвращает тип и разрешённые поля объекта только после серверного поиска и проверки роли пользователя.

Значение, которое имеет корректный формат `YUQ1`, но отсутствует в реестре, получает ошибку `UNISSUED_SYSTEM_CODE`. Его нельзя вручную связать с объектом: это предотвращает присвоение поддельного системного кода.

Resolver всегда read-only. Регистрация, замена и отзыв QR выполняются отдельными идемпотентными серверными командами с собственными проверками прав и аудитом.

## Доступ к resolver

Проверка роли выполняется на сервере. Текущие роли приложения сопоставляются так:

| Роль | Доступные цели | Возвращаемые данные |
| --- | --- | --- |
| `admin` | Корпуса, кабинеты и предметы во всех состояниях | Полная служебная карточка и точное состояние кода |
| `warehouse` (техник) | Корпуса, кабинеты и предметы | Рабочие поля для инвентаризации; для отозванной метки или неактивной цели — только безопасное состояние без персональных данных |
| `employee` (сотрудник) | Только активные предметы | Основные данные предмета и признак «свободен/закреплён» без имени чужого ответственного |
| `owner` | Нет доступа к QR-инвентаризации | Запрос отклоняется до обработки payload |

Семантика отказов:

- без действующей сессии endpoint возвращает HTTP `401` и `UNAUTHENTICATED`;
- роль без доступа к QR-инвентаризации получает HTTP `403` и `FORBIDDEN` до разбора payload;
- сотрудник при неизвестном коде, запрещённом типе цели, отозванном коде или неактивном объекте получает одинаковый HTTP `404` и `NOT_ACCESSIBLE`, чтобы нельзя было определить существование чужого объекта;
- техник и администратор получают точные доменные состояния `UNKNOWN`, `REVOKED`, `TARGET_INACTIVE` и `WRONG_CONTEXT` в пределах разрешённого рабочего потока;
- синтаксические ошибки `INVALID` и `UNSUPPORTED_VERSION` можно вернуть до поиска объекта, поскольку они не раскрывают его существование.

Все успешные ответы строятся из серверной проекции роли. Клиент не получает полную запись с последующим скрытием полей в интерфейсе.

## Распознавание уже нанесённых кодов

### Предметы

Legacy-код может быть автоматически распознан как официальный инвентарный номер предмета, только если одновременно выполняются условия:

- значение не входит в исчерпывающий набор placeholder-значений: пустая строка после нормализации, `-` или `??`;
- значение не входит в зарезервированное пространство системных идентификаторов;
- найден ровно один предмет с точным значением номера;
- официальный номер прошёл доменную валидацию;
- значение ещё не принадлежит другому объекту;
- поиск alias и официального номера даёт одну и ту же цель либо alias отсутствует.

Само распознавание не создаёт alias. Во время первоначальной миграции каждый валидный уникальный официальный номер заранее регистрируется как `legacy_raw` alias. Если администратор позднее меняет официальный номер, старое значение сохраняется как alias той же транзакцией, если оно не конфликтует с другим объектом. Благодаря этому старая наклейка продолжает работать без записи в базу при сканировании.

Значения `-`, `??`, пустая строка и строки только из пробелов означают отсутствие кода и не создают QR-запись при миграции.

### Корпуса и кабинеты

Автоматическое распознавание разрешено только по заранее импортированной таблице соответствий или по отдельно документированному legacy-формату. Название корпуса, номер кабинета и текущие прототипные ID не используются как автоматический идентификатор.

### Legacy URL

Старый URL может быть сохранён только как точный `legacy_url` alias. Resolver не переходит по нему и не доверяет host, path, query или fragment. Произвольные `http:`, `https:`, `javascript:` и `data:` значения никогда не исполняются.

### Неоднозначность и ручная привязка

Если точному значению соответствуют несколько объектов, resolver возвращает `AMBIGUOUS` и ничего не изменяет.

Перед миграцией, ручной привязкой legacy alias или изменением официального инвентарного номера сервер одной транзакцией проверяет:

- QR-реестр во всех статусах;
- текущие официальные инвентарные номера;
- зарезервированное пространство системных идентификаторов;
- исчерпывающий набор placeholder-значений.

Если значение уже относится к другому объекту или даёт несколько целей, операция отклоняется как `AMBIGUOUS`/`DUPLICATE`. Активный alias и официальный номер могут совпадать только тогда, когда оба указывают на один предмет. Конфликты исходных данных помещаются в отчёт миграции и не связываются автоматически.

Неизвестный legacy-код можно связать:

- технику — только при создании нового объекта;
- администратору — с существующим или новым объектом;
- сотруднику и роли `owner` — нельзя.

Ручная привязка выполняет все проверки пространств имён в транзакции и всегда создаёт аудит.

## Ответы resolver

Resolver использует устойчивые машинные коды ошибок, а интерфейс переводит сообщения на русский, казахский и английский:

| Код | Значение |
| --- | --- |
| `UNAUTHENTICATED` | Нет действующей сессии |
| `FORBIDDEN` | Роль не имеет доступа к QR-инвентаризации |
| `NOT_ACCESSIBLE` | Неперечисляющий ответ сотруднику для неизвестной или недоступной цели |
| `INVALID` | Значение не прошло входной фильтр или проверку формата |
| `UNSUPPORTED_VERSION` | Распознан зарезервированный системный префикс неизвестной версии |
| `UNKNOWN` | Допустимый legacy-код не найден |
| `UNISSUED_SYSTEM_CODE` | Формат системный, но такой токен не выдавался |
| `AMBIGUOUS` | Legacy-коду соответствует больше одного объекта |
| `REVOKED` | Код заменён или отозван |
| `DUPLICATE` | Значение уже связано с другим объектом |
| `TARGET_INACTIVE` | Код действителен, но объект архивирован или недоступен |
| `WRONG_CONTEXT` | Кабинет не принадлежит выбранному корпусу или предмет найден в другой локации |

Неизвестный, неправильный или неоднозначный код не сбрасывает прогресс текущей проверки.

## Безопасность и приватность

- Resolver требует действующую сессию.
- Ответ фильтруется по роли; сотрудник не получает имя текущего ответственного чужого предмета.
- Полный неизвестный payload не записывается в обычные application logs. Для корреляции используются длина, тип входа и `HMAC-SHA-256` с отдельным серверным диагностическим ключом и версией ключа; обычный несолёный хеш запрещён. Ротация ключа не требует повторной обработки ранее созданных записей.
- На resolver действуют ограничения размера запроса и частоты обращений.
- Повторный кадр камеры или сетевой retry не создаёт alias, результат или передачу повторно.
- Фотография или копия QR не является доказательством физического владения предметом.

## Требования к печати

- контрастный чёрный код на белом фоне;
- quiet zone не менее четырёх модулей;
- уровень коррекции ошибок не ниже `M`;
- под кодом печатается человекочитаемый payload или токен;
- макет проверяется реальными целевыми устройствами до массовой печати.

## Приёмочные примеры

| Вход | Ожидаемый результат |
| --- | --- |
| `YUQ1:7K3M9W2T8R5D4H6N1P0QX9C2BZ` | Поиск системного кода |
| `yuq1:7k3m9w2t8r5d4h6n1p0qx9c2bz` | Нормализация регистра и поиск |
| `7K3M9W2T8R5D4H6N1P0QX9C2BZ` через камеру или ручной ввод | Добавление `YUQ1:` и поиск того же объекта |
| корректный, но невыданный `YUQ1` | `UNISSUED_SYSTEM_CODE`, без ручной привязки |
| `YUQ2:...` | `UNSUPPORTED_VERSION`, без legacy-поиска |
| неправильный `YUQ1:...` | `INVALID`, без legacy-поиска |
| `2411/0162` | Точный поиск alias, затем единственного официального номера |
| `2411-0162` при наличии только `2411/0162` | `UNKNOWN`; разделитель не заменяется |
| `050-0002369` | Ведущие нули сохраняются |
| `-`, `??`, пустая строка | `INVALID`; alias не создаётся |
| legacy alias одного объекта совпал с официальным номером другого | `AMBIGUOUS`; операция привязки запрещена |
| legacy-код с двумя совпадениями | `AMBIGUOUS`; данные не меняются |
| отозванный код | `REVOKED`; значение не переиспользуется |
| код активного архивного объекта | `TARGET_INACTIVE`; данные объекта не изменяются |
| строка с NUL или bidi control | `INVALID` |
| URL неизвестного host | Точный поиск legacy alias без перехода по URL |

## Минимальный набор тестов реализации

- parser: валидный payload, голый токен одинаково для камеры и ручного ввода, регистр, BOM/CRLF, неверная длина, запрещённые символы, control chars, зарезервированные версии и malformed-системные префиксы;
- normalization: точный порядок обработки BOM, ASCII boundary whitespace, внутренних пробелов, не-ASCII spaces, invalid UTF-8 и лимита 512 байт одинаков для resolver, миграции и привязки;
- legacy: точное совпадение, ведущие нули, разные разделители, исчерпывающие placeholders, bare-token collision, alias-в-инвентарный конфликт и неоднозначность;
- resolver: корпус, кабинет, предмет, неизвестный, невыданный системный, отозванный, архивный и неправильный контекст;
- база данных: глобальная уникальность между типами, один active primary, сохранение уникальности отозванного кода и конкурентная вставка;
- миграция: повторяющиеся placeholders и конфликтующие пространства имён не создают записи;
- авторизация и приватность: техник, сотрудник, администратор и `owner`;
- non-enumeration: сотрудник получает одинаковый `NOT_ACCESSIBLE` для неизвестного, чужого типа, отозванного и неактивного объекта;
- идемпотентность: повтор сканирования и сетевой retry не создают дубликаты;
- E2E: генерация изображения, декодирование, resolver и тот же сценарий через ручной ввод.
