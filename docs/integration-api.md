# API чтения для внешнего сайта: товары, передачи и realtime

Базовый адрес после развёртывания: `https://inventory.yu.edu.kz/api/v1/integration`.
Это отдельная интеграция: ключи Facilities, Dockflow, общежитий и 1С сюда не подходят.

API предоставляет только просмотр данных и обновления SSE. Создавать товары,
выполнять передачи или изменять данные через него нельзя. Изменения, сделанные
сотрудниками и администраторами в Inventory, автоматически попадают в поток.
История событий начинается с установки миграций, а существующие данные
загружаются через коллекции.

## Что передать программисту

Передайте этот документ, базовый адрес и файл `read-*-consumer.env` из
`.private-transfer`. В нём находится `YU_INVENTORY_READ_API_KEY`.
Файл `read-*-server.env` с хешем устанавливается только на сервер Inventory.
Настройки БД, SESSION_SECRET и ключи других интеграций не требуются программисту.

Ключ хранится на сервере внешнего сайта. Он не должен попадать в JavaScript
браузера, `NEXT_PUBLIC_*`, URL, Git, логи или публичные страницы. Сервер внешнего
сайта проверяет права своих посетителей перед показом полученных данных.
Ключ даёт доступ ко всем перечисленным коллекциям организации; это доверенная
серверная интеграция, а не персональный доступ отдельного сотрудника.

## Выпуск и включение ключа

Из корня проекта:

```sh
node scripts/create-integration-key.mjs read
```

Команда создаёт два новых файла в игнорируемой Git папке `.private-transfer`:
consumer с секретом и server с SHA-256 хешем и сроком действия. Существующие
ключи не перезаписываются. Секрет содержит 256 случайных бит; срок — 90 дней.
Секрет не печатается в терминал. Ключ не включается автоматически.
Ранее выпущенный read-ключ продолжает подходить: перевыпуск не нужен.

На сервере Inventory:

1. Разверните код и примените миграции по разделу обновления ниже.
2. Добавьте две переменные из `read-*-server.env` в
   `/etc/yu-inventory/yu-inventory.env`, сохранив остальные настройки:

   ```dotenv
   INTEGRATION_API_READ_KEY_SHA256=<64 lowercase hex>
   INTEGRATION_API_READ_EXPIRES_AT=<ISO 8601 UTC>
   ```

3. Подготовьте runtime-окружение и перезапустите сервисы командами обновления.
   Изменения `.env.example` сами по себе не включают доступ.
4. Проверьте `GET /auth/check`, затем `/checkpoint`, `/items` и `/events`.

Старые ключи записи больше не принимаются, даже если их переменные остались
в окружении сервера. Ручки изменения данных удалены.

Для ротации добавьте новый хеш и срок в
`INTEGRATION_API_READ_KEY_SHA256_NEXT` и `INTEGRATION_API_READ_EXPIRES_AT_NEXT`,
затем подготовьте runtime-окружение и перезапустите сервис. После переключения
программиста перенесите новые значения в основные переменные, очистите `_NEXT`
и повторите подготовку runtime-окружения и перезапуск. Для отзыва удалите хеш.
Открытое SSE-соединение завершается максимум через 55 секунд.

## Обновление рабочего сайта

После push выполните на сервере:

```bash
cd /opt/yu-inventory/current
sudo -u yu-inventory git pull --ff-only origin master
sudo nano /etc/yu-inventory/yu-inventory.env
sudo bash deploy/update-integration-api.sh
```

В редакторе добавьте две строки из своего `read-*-server.env`, сохранив
существующие настройки. Этот локальный файл с настройками ключа не входит в Git.
Команда обновления проверяет чистоту исходников, создаёт и проверяет бэкап,
применяет миграции, собирает сайт, обновляет runtime-окружение и проверяет запуск.
При ошибке выполнение останавливается; после остановки сервисов сайт остаётся
недоступен до исправления причины и повторного успешного запуска команды.
Один `git push` сайт не обновляет.

## Авторизация и ограничения

Каждый запрос: `Authorization: Bearer <секрет из consumer.env>`.
Cookies пользователя не заменяют ключ. API не разрешает CORS и отклоняет запросы
с заголовком `Origin`: внешний браузер обращается к своему серверу, тот — к Inventory.

Лимиты хранятся в PostgreSQL и применяются к ключу независимо от IP и количества
процессов: чтение — 120 запросов/минуту, начало SSE — 6.
При недоступности хранилища лимитов API закрывает доступ с `503`.
Успешные и ошибочные ответы не кэшируются. Сравнение хешей ключей выполняется
через `timingSafeEqual`. Ошибки не раскрывают SQL, адреса БД или секреты.

HTTPS и передача секретов в заголовках следуют
[рекомендациям OWASP для REST API](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).

## Чтение

| Метод и путь | Назначение |
| --- | --- |
| `GET /auth/check` | Проверить ключ, получить список коллекций |
| `GET /checkpoint` | Получить безопасный начальный курсор событий |
| `GET /<коллекция>?limit=100&after=<UUID>` | Страница данных |
| `GET /changes?after=<курсор>&limit=100` | Надёжное получение событий страницами |
| `GET /events?after=<курсор>&limit=100` | SSE с теми же событиями |

`limit`: целое число от 1 до 100, по умолчанию 100. Неизвестные и повторяющиеся
параметры отклоняются. Курсоры коллекций — UUID последней записи; курсоры событий
имеют вид `номерТранзакции:номерСобытия`. Они являются непрозрачными строками:
не преобразовывайте их в JavaScript Number, не увеличивайте и не сравнивайте как текст.
Курсор из будущего возвращает `400 cursor_ahead_of_feed`.

Ответ коллекции:

```json
{"data":[{"id":"UUID","name":"Стол"}],"nextCursor":"UUID или null"}
```

Продолжайте с `after=nextCursor`, пока `nextCursor` не станет `null`.
Коллекции возвращают и архивные/закрытые записи; применяйте фильтры по статусам
на стороне потребителя. UUID-поля связывают коллекции друг с другом.

| Коллекция | Данные |
| --- | --- |
| `items` | Название, категория, раздел general/it, бренд, модель, количество, цена, инвентарный номер, помещение, статус, состояние, авторы, даты и версия |
| `employees` | ID, ФИО, подразделение, должность, роль, активность, дата удаления и версия |
| `buildings` | ID, название, адрес, статус и даты |
| `rooms` | ID, корпус, обозначение, этаж, основной ответственный, статус и даты |
| `responsibilities` | Периоды ответственности: товар, сотрудник, источник, начало и завершение |
| `assignments` | Количественные передачи/партии, штрихкод, количество, сотрудник, помещение, предыдущее размещение, статус |
| `transfers` | Прежний механизм передачи ответственности, участники, статусы и административный результат |
| `transfer-requests` | Новый механизм передачи: инициатор, получатель, статус, срок, закрытие, административное решение и версия |
| `transfer-request-items` | Товары заявки, количество, исходная партия, результат и версии |
| `service-requests` | Товар, помещение, автор, тип, статус и даты сервисной заявки |
| `inspections` | Название проверки, исполнитель, статус, срок и даты |

Точные поля перечислены в `lib/server/integration-projections.ts`; события используют
тот же список полей. Цена `unitPrice` передаётся десятичной строкой, например `"100.00"`.
Поля ИИН, email, телефон, пароли, OAuth-данные, QR-секреты, сетевые адреса, фото,
внутренние комментарии и свободный текст сервисных заявок не экспортируются.
Для текущего ответственного используйте `responsibilities` с `endedAt=null`;
для количественных выдач — `assignments` со `status="active"`.
Статус `pending` заявки сам по себе не означает, что ответственность уже передана.

## Начальная синхронизация без пропуска изменений

1. Сохраните `cursor` из `GET /checkpoint` **до** загрузки коллекций.
2. Загрузите все страницы нужных коллекций во временное хранилище внешнего сайта.
3. Получайте `/changes?after=<сохранённый курсор>` до `hasMore=false` и применяйте
   события в порядке ответа. При каждой странице сохраняйте `nextCursor`.
4. Опубликуйте полученный снимок и подключите SSE с этим курсором.

`upsert` заменяет запись с данным ID, `delete` удаляет её. API возвращает последнее
зафиксированное состояние затронутой записи на момент запроса, а не исторический
снимок каждого промежуточного изменения. Это предотвращает возврат к старым данным,
если более старая по xid транзакция изменила запись позже новой транзакции.
Поле `revision` — строковый номер последнего изменения данной записи, независимый
от курсора доставки; при наличии
локальной версии применяйте только большую revision (сравнивайте через BigInt),
включая сохранение revision для удалённых записей. Повторное применение
события должно быть безопасным. Сохраняйте данные и курсор одной локальной транзакцией.
Если операция не применена, не сохраняйте её курсор. При переподключении возможны
повторы — доставка рассчитана на идемпотентного потребителя, без гарантии exactly-once.

```json
{
  "changes": [{
    "cursor": "12345:678",
    "revision": "678",
    "entity": "items",
    "operation": "upsert",
    "recordId": "UUID",
    "data": {"id":"UUID","name":"Стол","quantity":1,"unitPrice":"100.00"},
    "occurredAt": "2026-11-06T10:00:00+00:00"
  }],
  "nextCursor": "12345:9223372036854775807",
  "hasMore": false
}
```

При `delete` значение `data=null`. События фиксируются триггерами в транзакции
самой операции: откат не оставляет ложного события. Порядок строится по xid8
транзакции и ID события. Поток не продвигается через незавершённые старые транзакции:
это предотвращает потерю событий при разном порядке commit. Длительная открытая
транзакция в БД может задерживать поток до её завершения; отслеживайте такие транзакции.
Журнал не очищается автоматически — контролируйте его размер и резервное копирование;
не удаляйте события вручную, пока потребители используют старые курсоры.

## Realtime SSE

Сервер внешнего сайта открывает поток через `fetch` с Authorization.
Встроенный браузерный EventSource не подходит для хранения серверного ключа.
Проверка новых событий — каждые 2 секунды, если нет задерживающих транзакций.
Каждое соединение завершается через 55 секунд: переподключайтесь с последним
сохранённым курсором, делая паузу 1–3 секунды и учитывая `Retry-After` при `429/503`.

Формат:

```text
id: 12345:678
event: change
data: {"cursor":"12345:678","revision":"678","entity":"items","operation":"upsert","recordId":"UUID","data":{"id":"UUID","name":"Стол"},"occurredAt":"..."}

id: 12345:9223372036854775807
event: checkpoint
data: {"cursor":"12345:9223372036854775807"}

```

`change`: применить актуальные данные с учётом revision, затем сохранить курсор.
`checkpoint`: сохранить курсор после применения предыдущих событий; приходит и
когда изменений нет. `revoked`: ключ недействителен, остановиться.
`unavailable`: переподключиться после задержки. Обычный EOF требует переподключения.
Заголовок `Last-Event-ID` имеет приоритет над `after` для восстановления SSE.
Если ваш хостинг буферизует/обрывает поток, можно опрашивать `/changes` каждые 2 секунды.

## Ошибки и проверка

| Код | Действие потребителя |
| --- | --- |
| 400 | Исправить параметры или курсор |
| 401 | Проверить ключ, срок действия и ротацию |
| 403 | Выполнять запросы с сервера без Origin |
| 404 | Неизвестная коллекция или маршрут |
| 405 | Использовать GET; операции изменения данных отсутствуют |
| 429 | Подождать Retry-After |
| 503 | Проверить БД/конфигурацию, повторить после задержки |

Команды проверки из корня проекта:

```sh
node --conditions=react-server --import tsx --test tests/integration-api.test.ts
node scripts/test-database-local.mjs integration-api.test.ts
node node_modules/typescript/bin/tsc --project tests/typecheck/tsconfig.integration-api.json --pretty false
```

PostgreSQL-проверка запускает отдельную временную БД на Windows x64 и удаляет её
после выполнения. Она проверяет миграцию, реальные права runtime-роли, откаты,
параллельный порядок commit, защиту журнала, смену ответственного
внутри Inventory и лимиты доступа. Проверки маршрута подтверждают отсутствие
POST/PUT/PATCH/DELETE и отказ старым ключам записи.
