# Техническое задание: управление доступом к кабинетам

## 1. Цель

Добавить управляемую администратором видимость кабинетов и находящихся в них ТМЦ.

Для каждого кабинета должен храниться один из двух режимов:

- **Открытый доступ** — при открытии кабинета пользователь может просмотреть все находящиеся в нём ТМЦ и увидеть, за кем они закреплены.
- **Закрытый доступ** — полное содержимое доступно только администратору и кладовщику. Обычный сотрудник видит только закреплённые лично за ним ТМЦ.

Ограничение должно действовать одинаково на карте объектов, в списках, при переходе по прямой ссылке и при сканировании QR-кода кабинета.

## 2. Связь с существующим ТЗ

Это ТЗ дополняет `docs/TZ-inventory-list-filters-transfer-campus-card.md` и не отменяет уже описанные в нём требования:

- роли **администратор**, **кладовщик** (`warehouse`) и **сотрудник** (`employee`);
- навигацию **объект → этаж → кабинет → ТМЦ**;
- действующие QR-коды кабинетов;
- сохранение безопасного `returnTo` после авторизации;
- серверную проверку прав доступа;
- поддержку русского, казахского и английского интерфейсов.

Если требования пересекаются, правила доступа к кабинетам из настоящего документа имеют приоритет.

## 3. Термины

- **Свои ТМЦ сотрудника** — ТМЦ, у которых текущий сотрудник указан ответственным. Сюда также входят локальные группы штрихкодов, если по действующим правилам они закреплены за этим сотрудником.
- **Полный просмотр кабинета** — просмотр данных кабинета, полного списка его ТМЦ и ответственного по каждому ТМЦ.
- **Ограниченный просмотр кабинета** — просмотр только своих ТМЦ без раскрытия чужих ТМЦ, их количества, ответственных и других сведений.
- **Нет доступа** — экран с сообщением **«Доступ к кабинету закрыт»** без раскрытия названия кабинета и его содержимого.

## 4. Модель доступа

### 4.1. Поле кабинета

Добавить кабинету поле режима доступа, например `accessMode`:

- `open` — открытый доступ;
- `closed` — закрытый доступ.

Требования к полю:

1. Поле обязательно и не может быть `null`.
2. Для нового кабинета значение по умолчанию — `open`.
3. Всем кабинетам, существующим на момент внедрения, миграция устанавливает `open`.
4. Хранится только текущее значение. Отдельная история изменений режима доступа не создаётся.
5. Изменение режима должно участвовать в существующем механизме версии кабинета, чтобы устаревшее параллельное изменение не перезаписывало актуальное.

### 4.2. Матрица прав

| Роль и условие | Открытый кабинет | Закрытый кабинет |
| --- | --- | --- |
| Администратор | Полный просмотр | Полный просмотр |
| Кладовщик | Полный просмотр | Полный просмотр |
| Сотрудник, в кабинете есть его ТМЦ | Полный просмотр | Ограниченный просмотр: только свои ТМЦ |
| Сотрудник, в кабинете нет его ТМЦ | Полный просмотр по QR-коду или разрешённой прямой ссылке; на его карте кабинет не показывается | Нет доступа |

Только администратор может изменять режим доступа. Кладовщик может просматривать закрытые кабинеты, но не может открывать или закрывать доступ.

## 5. Карта объектов для сотрудника

1. На карте сотрудника показывать только кабинеты, в которых находится хотя бы один закреплённый за ним ТМЦ.
2. Правило действует как для открытых, так и для закрытых кабинетов.
3. В открытом кабинете сотрудник может открыть полный список ТМЦ и увидеть ответственных.
4. В закрытом кабинете сотрудник видит только свои ТМЦ.
5. Чужие ТМЦ закрытого кабинета не должны влиять на видимые сотруднику счётчики, суммы, подписи, состояния пустого списка или другие агрегаты.
6. Если последний ТМЦ сотрудника перенесён из кабинета или передан другому ответственному, этот кабинет перестаёт отображаться на карте сотрудника.
7. Кабинеты без ТМЦ сотрудника не показывать на его карте независимо от режима доступа.
8. Для администратора и кладовщика карта продолжает показывать все доступные им кабинеты, включая закрытые.

## 6. Список ТМЦ и карточка кабинета

### 6.1. Открытый кабинет

При открытии кабинета администратор, кладовщик и сотрудник видят:

- полный список находящихся в кабинете ТМЦ;
- предусмотренные существующим интерфейсом сведения о ТМЦ;
- ответственного по каждому ТМЦ.

Открытый режим кабинета не предоставляет сотруднику административные действия над чужими ТМЦ. Возможность изменения, передачи, списания и других операций по-прежнему определяется существующими правами роли.

### 6.2. Закрытый кабинет

Администратор и кладовщик видят кабинет и все его ТМЦ без дополнительных ограничений.

Для сотрудника:

1. Если в кабинете есть его ТМЦ, показать карточку кабинета в ограниченном режиме и вывести только эти ТМЦ.
2. Не возвращать на клиент сведения о чужих ТМЦ.
3. Не показывать количество чужих ТМЦ, их стоимость, статусы, категории, фотографии, инвентарные номера и ответственных.
4. Поиск, фильтры, показатели и экспорт не должны позволять обнаружить чужие ТМЦ закрытого кабинета.
5. Если своих ТМЦ в кабинете нет, вместо карточки показать только **«Доступ к кабинету закрыт»**.

В общем списке ТМЦ сотрудника из закрытых кабинетов остаются видимыми только закреплённые за ним ТМЦ. Доступ к чужим ТМЦ не должен появляться через изменение URL, параметров фильтра или прямой API-запрос.

## 7. Сканирование QR-кода кабинета

После распознавания действующего QR-кода сервер определяет кабинет, текущего пользователя, его роль, режим кабинета и наличие его ТМЦ.

### 7.1. Открытый кабинет

После авторизации пользователь открывает кабинет и видит полный список ТМЦ с ответственными согласно разделу 6.1.

### 7.2. Закрытый кабинет

- Администратор и кладовщик получают полный просмотр.
- Сотрудник, у которого в кабинете есть свои ТМЦ, получает ограниченный просмотр только этих ТМЦ.
- Сотрудник без своих ТМЦ видит только сообщение **«Доступ к кабинету закрыт»**.

На экране отказа запрещено показывать название или номер кабинета, корпус, этаж, количество ТМЦ, ответственных и любые другие сведения о кабинете.

Неавторизованный пользователь проходит существующий сценарий авторизации с безопасным возвратом на отсканированную ссылку. До определения роли и прав содержимое кабинета не раскрывается.

Недействующий или неизвестный QR-код продолжает обрабатываться как «не найден» и не должен ошибочно показывать сообщение о закрытом доступе.

## 8. Управление доступом администратором

### 8.1. Создание кабинета

1. В форму создания кабинета добавить поле **«Доступ к кабинету»**.
2. Варианты: **«Открытый доступ»** и **«Закрытый доступ»**.
3. По умолчанию выбран **«Открытый доступ»**.
4. Выбранное значение сохраняется вместе с кабинетом.
5. Кладовщик не получает право задавать режим доступа при создании кабинета, если создание кабинетов для него допускается другими требованиями.

### 8.2. Одиночное изменение

1. В административной карточке кабинета показывать текущий режим доступа.
2. Добавить действие **«Открыть доступ»** для закрытого кабинета и **«Закрыть доступ»** для открытого.
3. Одиночное изменение применяется сразу после действия без отдельного окна подтверждения.
4. После успешного изменения интерфейс сразу показывает новый режим.
5. При ошибке режим в интерфейсе не должен меняться; показать понятное сообщение об ошибке.

### 8.3. Массовое изменение

В разделе **«Объекты → Кабинеты»**:

1. Добавить ручной выбор нескольких кабинетов флажками.
2. Для выбранных кабинетов показать действия **«Открыть доступ»** и **«Закрыть доступ»**.
3. Автоматический выбор всех кабинетов объекта или всех результатов фильтра не требуется.
4. Перед массовым изменением показать подтверждение с выбранным режимом и количеством кабинетов.
5. Изменение выполняется только после подтверждения.
6. После завершения показать итог: сколько кабинетов изменено и какие кабинеты не удалось изменить.
7. Повторная установка уже действующего режима допустима и считается идемпотентной: кабинет остаётся без изменения, операция не создаёт ошибку.
8. Если используется частичный результат, сервер должен вернуть результат по каждому кабинету. Нельзя показывать общий успех, если часть кабинетов не обновлена.

## 9. Серверные требования и защита данных

1. Все правила из матрицы доступа проверять на сервере при каждом чтении кабинета и его ТМЦ.
2. Клиентская фильтрация не считается защитой. Запрещённые записи не должны попадать в HTML, RSC-данные, JSON-ответы или экспорт.
3. Эндпоинты чтения кабинета по ID и по QR-коду должны применять одинаковые правила.
4. Списки кабинетов, данные карты, поиск, фильтры, показатели и выгрузки должны использовать ту же область видимости.
5. Обычный сотрудник не может изменить `accessMode`, в том числе через прямой API-запрос или подмену полей формы.
6. Кладовщик не может изменить `accessMode`.
7. Массовое изменение доступно только администратору и принимает только явный список ID выбранных кабинетов и целевой режим.
8. Сервер валидирует существование кабинетов, их актуальные версии и допустимость значения режима.
9. Архивные и отсутствующие кабинеты обрабатываются по существующим правилам и не должны становиться доступными из-за нового режима.
10. Ответ об отказе не должен позволять отличить закрытый кабинет от другого недоступного ресурса по содержащимся в теле ответа данным. В пользовательском интерфейсе выводится согласованный текст **«Доступ к кабинету закрыт»**.

## 10. Интерфейс и локализация

1. Все новые подписи, статусы, кнопки, подтверждения и ошибки добавить на русском, казахском и английском языках.
2. В административных списках визуально различать открытые и закрытые кабинеты понятной меткой доступа.
3. Метка не заменяет серверную проверку прав.
4. Управление должно работать на настольном и мобильном экране.
5. Флажки массового выбора и кнопки действий должны быть доступны с клавиатуры и иметь понятные доступные названия.
6. Во время сохранения блокировать повторную отправку того же действия и показывать состояние загрузки.

## 11. Критерии приёмки

1. Новый кабинет без изменения поля создаётся открытым.
2. При создании администратор может выбрать закрытый режим.
3. После миграции все ранее существовавшие кабинеты открыты.
4. Администратор может открыть или закрыть один кабинет из его карточки без окна подтверждения.
5. Администратор может вручную выбрать несколько кабинетов и массово открыть или закрыть их после подтверждения.
6. Кладовщик видит полное содержимое открытых и закрытых кабинетов, но не может менять режим.
7. Сотрудник видит на карте только кабинеты со своими ТМЦ.
8. В открытом кабинете сотрудник видит все ТМЦ и их ответственных, но не получает дополнительных прав на изменение чужих ТМЦ.
9. В закрытом кабинете сотрудник видит только свои ТМЦ.
10. Закрытый кабинет без ТМЦ сотрудника не отображается на его карте.
11. При сканировании такого кабинета сотрудник видит только **«Доступ к кабинету закрыт»**, без названия и других данных.
12. При сканировании закрытого кабинета со своим ТМЦ сотрудник видит только свои ТМЦ.
13. Прямая ссылка, изменение URL, фильтры и прямой API-запрос не позволяют сотруднику получить чужие ТМЦ закрытого кабинета.
14. После переноса последнего ТМЦ сотрудника из закрытого кабинета доступ сотрудника к просмотру этого кабинета прекращается.
15. Неизвестный QR-код показывает состояние «не найден», а не «доступ закрыт».
16. Все новые состояния корректно отображаются на русском, казахском и английском языках.

## 12. Обязательные проверки перед сдачей

- модульные тесты матрицы доступа для обеих настроек кабинета и всех трёх ролей;
- тест сотрудника с собственным и без собственного ТМЦ в закрытом кабинете;
- тест отсутствия чужих данных в серверном ответе ограниченного просмотра;
- тесты чтения кабинета по ID и QR-коду;
- тест карты сотрудника до и после переноса его последнего ТМЦ;
- тест создания кабинета с режимом по умолчанию и с явно выбранным режимом;
- тест одиночного изменения доступа и конфликта версий;
- тест массового изменения, подтверждения, частичного результата и повторной установки того же режима;
- тест запрета изменения режима для кладовщика и сотрудника;
- тест отсутствия утечки через поиск, фильтры, показатели и экспорт;
- тест миграции существующих кабинетов в режим `open`;
- компонентные тесты мобильного и настольного интерфейса;
- проверка сборки, типов и локализаций.
