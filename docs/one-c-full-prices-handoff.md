# Полная стоимость ОС и цена МП: согласование выгрузки

Дата: 4 ноября 2026 года.

## Сообщение программисту 1С

Добрый день! Уточняем требования к стоимости в выгрузках ОС и материалов.
Для карточек Inventory нужна фактическая полная стоимость конкретного предмета,
а не его остаточная стоимость после амортизации.

1. **ОС:** прежний `POST /api/integrations/1c/fixed-assets`. Для каждого ОС,
   включая полностью самортизированные, передавайте `InitialCost` — первоначальную
   стоимость до вычета амортизации. `ResidualValue` передавайте отдельно; ноль в
   этом поле допустим. Например: `InitialCost=186990.00`, `ResidualValue=0.00`.
   GUID и инвентарные номера должны оставаться прежними. Для индивидуального
   предмета передавайте `Quantity=1`. Если в 1С есть групповые ОС, согласуем
   их отдельно: общую стоимость группы нельзя подставлять в цену одного предмета.
2. **Материалы:** прежний `POST /api/integrations/1c/materials`, `SchemaVersion=2`.
   Для каждой строки с положительным остатком передавайте `UnitPrice` — полную
   учётную цену **одной единицы именно этой позиции**. Отдельно передавайте
   количество, счёт, склад и устойчивый код/GUID МОЛ. Разные цены у разных МОЛ,
   счетов или складов сохраняйте отдельными строками. При 7 штуках по 9100.50
   отправляйте `Quantity=7`, `UnitPrice=9100.50`, а не общую сумму 63703.50.
3. Отправьте полный актуальный перечень ОС и остатков материалов, включая
   обновления `Quantity=0` по израсходованным остаткам и прежним МОЛ при передаче.
   Для материалов используйте новую фактическую дату `SnapshotAt` с часовым поясом.
4. После согласованного развёртывания API будет возвращать HTTP `422`, если
   первоначальная стоимость ОС не указана/нулевая или у положительного остатка МП
   отсутствует положительная цена. Ответ укажет проблемные GUID/коды и строки.
   Исправлять и повторять нужно весь отклонённый пакет. Нулевые остатки МП
   принимаются без цены, чтобы корректно отражать расход.
5. Сначала проверим один полностью самортизированный ОС и две позиции материалов
   с разными ценами. После проверки отправьте полный перечень. Просим сообщить
   число выгруженных ОС, число строк остатков и `requestId` успешных ответов,
   чтобы сверить полноту приёма. При неизвестной или действительно нулевой полной
   стоимости сообщите об исключении; фиктивные суммы передавать не нужно.

Авторизация остаётся `Authorization: Bearer <API_KEY>`. ОС и МП используют свои
отдельные ключи. Значения ключей передаются по согласованному закрытому каналу.
Полные контракты: [ОС](one-c-fixed-assets-api.md), [материалы](one-c-materials-api.md).

## Проверка на стороне Inventory

1. После обновления сервера проверить `GET` обоих endpoint: `configured=true`,
   у ОС `pricing.field=InitialCost`, у МП `pricing.field=UnitPrice`.
2. Подтвердить, что тестовый ОС содержит `InitialCost=186990.00`, а
   `ResidualValue=0.00`; материалы сохранили цену за единицу и отдельные МОЛ.
3. Открыть `/integrations/1c`, нажать «Обновить», затем во вкладке ОС или МП
   нажать «Проверить изменения». Проверить предложенные цены и причины пропуска.
4. Применить просмотренный план. Это общий план: фильтр таблицы ограничивает
   отображение, а не набор применяемых изменений. Импорт сам карточки не меняет.
5. Скачать Excel и сверить число принятых строк с числами отправителя.
   Полноту списка 1С нельзя доказать только по успешно принятому пакету.

Суммы без источника не вычисляются. Неоднозначная привязка или разные цены
не разрешают подстановку произвольной стоимости; такие карточки требуют сверки.

## Обновление сервера

После получения нового коммита из `origin/master` выполнить от root:

```bash
bash /opt/yu-inventory/current/deploy/update-one-c-prices.sh
```

Скрипт проверяет чистоту checkout и резервную копию, устанавливает зависимости,
применяет миграции, проверяет БД, собирает приложение и перезапускает сервисы.
В конце проверяет capability обоих API. Он не отправляет выгрузки из 1С и не
применяет изменения карточек. При ошибке сборки сервисы могут остаться остановлены:
исправить показанную причину и повторить скрипт.
