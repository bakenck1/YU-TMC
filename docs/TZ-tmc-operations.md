# Техническое задание: операции с ТМЦ

## 1. Назначение

Добавить в существующий сайт YU Inventory полноценный модуль операций с ТМЦ:

- принять ТМЦ;
- выдать ТМЦ;
- переместить ответственность за ТМЦ между пользователями;
- изменить локацию ТМЦ;
- просматривать историю заявок и решений;
- получать уведомления о новых заявках.

Модуль реализуется внутри текущего проекта, текущей авторизации, PostgreSQL,
ролей, аудита, QR-сканера, локализации и существующих API. Отдельное приложение,
отдельная база пользователей или параллельная система заявок не создаются.

## 2. Согласованные решения

### 2.1. Пользователи и права

Используются существующие роли `admin`, `warehouse`, `employee`.

- Любой активный пользователь может принять свободный ТМЦ сканированием QR.
- Занятый ТМЦ может передавать текущий ответственный или администратор.
- Администратор может выполнять операции для любых ТМЦ.
- Новый ответственный выбирается среди активных пользователей, кроме самого себя.
- В выборе показываются ФИО, логин и роль.
- «Изменить локацию» доступно только администратору.
- Сотрудник видит и выбирает для массовых операций только свои ТМЦ.
- Администратор может выбрать ТМЦ разных текущих ответственных.

### 2.2. Локация

Объект и помещение выбираются только из существующих справочников университета:

`объект/корпус → помещение/кабинет`.

Свободный текст и создание новых объектов из формы запрещены.

«Перемещение ТМЦ» меняет только ответственного. Фактическая локация не меняется.
Локацию изменяет только администратор через отдельную операцию.

### 2.3. Заявка на передачу ответственности

При передаче занятого ТМЦ создаётся заявка между текущим и новым ответственным.
До решения текущий ответственный не меняется.

- Получатель может принять все ТМЦ или выбрать только часть галочками.
- Снятая галочка означает отказ по конкретному ТМЦ.
- Принятые ТМЦ автоматически переходят новому ответственному.
- Отклонённые ТМЦ остаются у прежнего ответственного.
- Отказ не требует причины.
- Комментарий при создании заявки необязателен.
- Создатель может отменить заявку до решения.
- После отправки заявка неизменяема: редактирование выполняется через отмену и новую заявку.
- Администратор может принять, отклонить или отменить любую заявку.
- Принудительное решение администратора требует комментария.

### 2.4. Массовые операции

Одна операция может содержать от 1 до 50 ТМЦ.

В БД создаётся одна родительская заявка и отдельная позиция для каждого ТМЦ.
Каждая позиция имеет собственный результат и собственную запись аудита.

Проблемные позиции не блокируют корректные:

- проблемная позиция исключается из отправки;
- пользователю показывается причина исключения;
- корректные позиции отправляются;
- результат отображается отдельно по каждой позиции.

Примеры проблем: уже есть активная заявка, ТМЦ списан, нет права доступа,
ТМЦ отсутствует или текущий ответственный уже изменился.

### 2.5. Статусы

Общие статусы заявки:

- `Ожидает`;
- `Принята`;
- `Отклонена`;
- `Отменена`.

Пока есть необработанные позиции, заявка имеет статус `Ожидает`.
После обработки всех позиций:

- хотя бы одна принята — общая заявка `Принята`;
- все отклонены — общая заявка `Отклонена`.

Для каждой позиции дополнительно хранится результат: ожидает, принято,
отклонено, отменено, недействительно.

Если текущий ответственный изменился до решения, заявка по позиции становится
недействительной и принять её нельзя.

## 3. UX: телефон

На главном экране добавить пункт **«Принять / Выдать ТМЦ»**.

Экран содержит три крупные кнопки:

1. **Принять**
2. **Выдать**
3. **Перемещение ТМЦ**

Ниже расположить кнопку **«История заявок»**.

### 3.1. Принять свободный ТМЦ

1. Пользователь нажимает «Принять».
2. Открывается QR-сканер.
3. После успешного сканирования показывается карточка ТМЦ.
4. Пользователь нажимает «Принять ТМЦ».
5. ТМЦ сразу закрепляется за ним.
6. Локация не меняется.
7. Показывается результат операции и ссылка на историю.

### 3.2. Выдать ТМЦ

1. Пользователь открывает «Выдать».
2. Сканирует QR или выбирает ТМЦ из списка.
3. Выбирает одного активного пользователя поиском по ФИО/логину.
4. При необходимости добавляет комментарий.
5. Просматривает полную карточку операции.
6. Нажимает «Отправить заявку».
7. Получатель получает push и внутрисистемное уведомление.

### 3.3. Перемещение ТМЦ

Форма содержит:

- список выбранных ТМЦ;
- фото, название, QR/инвентарный номер, количество;
- текущего ответственного;
- нового ответственного;
- объект и помещение как контекст операции;
- необязательный комментарий;
- кнопки «Отмена» и «Подтвердить».

Объект и помещение не изменяются этой операцией.

### 3.4. Принятие групповой заявки

Push-уведомление открывает непосредственно карточку заявки.

Карточка содержит:

- список ТМЦ с чекбоксами;
- кнопку «Принять все»;
- кнопку «Принять выбранные»;
- фото, название, QR/инвентарный номер, количество;
- текущего и нового ответственного;
- объект, помещение, инициатора, дату, комментарий и стоимость.

Снятые позиции получают отказ. После подтверждения показывается итог:
«Принято N из M».

## 4. UX: компьютер

В существующем «Списке ТМЦ» сохраняется текущая таблица.

После выбора строк показывается верхняя панель действий:

- «Изменить локацию» — только администратор;
- «Перемещение ТМЦ» — текущий ответственный или администратор;
- существующие действия проекта — согласно текущей ролевой модели.

### 4.1. Поиск пользователя

Использовать searchable combobox с подсказками по ФИО и логину.
В результате отображать ФИО, логин и роль. Себя выбрать нельзя.

### 4.2. Изменение локации администратором

Администратор может выбрать несколько ТМЦ, выбрать объект и помещение и
подтвердить массовое изменение. Корректные позиции обновляются, проблемные
отображаются отдельно. Старая и новая локация записываются в историю.
Комментарий необязателен.

## 5. Уведомления

Каналы:

- внутрисистемные уведомления;
- Web Push;
- счётчик непрочитанных уведомлений.

Получатель получает уведомление о новой заявке.
Инициатор получает одно сводное уведомление о результате, например
«Принято 17 из 20».
Текущий ответственный получает уведомление о передаче.
Администратор получает уведомления о просроченных и проблемных заявках.

Заявка старше 24 часов получает признак «Просроченная» для администратора.
Автоматическая передача или отмена не выполняется.

## 6. История и аудит

Участники видят свои заявки и связанные операции.
Администратор видит всю историю.

Фильтры истории:

- статус;
- период;
- инициатор;
- получатель;
- объект;
- помещение;
- ТМЦ;
- просроченные заявки.

Экспорт истории отдельным файлом не реализуется.

Операции и решения не удаляются. Разрешено удалять только персональные
комментарии; удаление комментария само записывается в аудит.

Аудит каждой операции должен содержать:

- actor/user id;
- время;
- ТМЦ;
- старого и нового ответственного;
- старую и новую локацию для location-change;
- действие и результат;
- родительскую заявку и позицию;
- комментарий, если есть;
- причину отказа администратора, если применимо.

## 7. Backend и данные

Добавить в существующую PostgreSQL-модель сущности:

- `tmc_transfer_requests` — родительская заявка;
- `tmc_transfer_request_items` — позиции заявки;
- `tmc_operation_notifications` — внутрисистемные уведомления;
- необходимые индексы для статуса, получателя, инициатора, срока и ТМЦ.

Все изменения выполняются доменными сервисами и транзакциями.
Клиент не является источником прав или итогового состояния.

Нужны атомарные проверки:

- текущий ответственный не изменился;
- нет второй активной заявки на один ТМЦ;
- ТМЦ активен;
- пользователь активен и не равен инициатору;
- заявитель имеет право операции;
- массовая операция не превышает 50 позиций.

Рекомендуемые API внутри существующего маршрутизатора:

- `POST /api/inventory/transfer-requests`;
- `GET /api/inventory/transfer-requests`;
- `GET /api/inventory/transfer-requests/[id]`;
- `POST /api/inventory/transfer-requests/[id]/decision`;
- `POST /api/inventory/transfer-requests/[id]/cancel`;
- `POST /api/inventory/items/bulk-location` — admin-only;
- `GET /api/notifications`;
- `POST /api/notifications/[id]/read`.

Имена маршрутов могут быть адаптированы под существующие endpoints, но новые
параллельные механизмы авторизации запрещены.

## 8. Безопасность

- Проверять права на сервере для каждой операции.
- Не доверять выбранному пользователем ответственному или локации.
- Не раскрывать чужие заявки обычному пользователю.
- Использовать UUID/opaque ids и parent-scope authorization.
- Не хранить секреты или персональные данные в QR.
- Ограничить размер всех запросов и массовых операций.
- Использовать idempotency key для подтверждений и повторов мобильного клиента.
- Повторный запрос не должен создавать дубль заявки или повторно менять ответственность.
- Добавить тесты BOLA/IDOR, race condition и replay.

## 9. TDD: обязательная методология

TDD — Test-Driven Development: сначала пишется тест ожидаемого поведения,
затем минимальная реализация, затем безопасный рефакторинг.

Для каждой задачи использовать цикл:

1. **Red** — написать падающий тест.
2. **Green** — реализовать минимальный код, чтобы тест прошёл.
3. **Refactor** — улучшить код без изменения поведения.

TDD обязателен для:

- прав ролей;
- свободного принятия;
- создания заявки;
- массовой заявки;
- частичного принятия;
- отказа и отмены;
- просрочки;
- изменения локации admin-only;
- уведомлений;
- истории и фильтров;
- конкурирующих запросов;
- повторной отправки и idempotency;
- security/BOLA/IDOR;
- мобильных ключевых экранов.

Минимальные acceptance tests:

- свободный ТМЦ принимается один раз;
- занятый ТМЦ создаёт заявку, но не меняет ответственного до принятия;
- получатель может принять выбранные 17 из 20;
- снятые позиции отклоняются;
- новая заявка на ТМЦ с активной заявкой блокируется;
- устаревшая заявка не принимается после смены ответственного;
- сотрудник не может передать чужой ТМЦ;
- администратор может выполнить массовое изменение локации;
- сотрудник не может изменить локацию;
- повтор POST с тем же idempotency key не создаёт дубль;
- push открывает нужную заявку;
- история показывает корректные старые и новые значения;
- каждый endpoint проверяет authorization scope.

## 11. Definition of Done

Функционал считается готовым только если:

- реализован в текущем сайте, а не в отдельном приложении;
- есть миграция PostgreSQL;
- есть серверные permissions и транзакции;
- есть RU/KZ/EN переводы;
- мобильный и desktop-сценарии работают через общий API;
- есть TDD-тесты Red → Green → Refactor;
- проходят unit, integration, security и UI tests;
- проверены массовые операции до 50 ТМЦ;
- проверены принятие, отказ, отмена, просрочка и частичный результат;
- проверены конкурентные изменения и повторные запросы;
- обновлена документация и история аудита;
- существующие сценарии сайта не сломаны.
