# Поля, валидация и ошибки QR-инвентаризации

## Статус документа

Этот документ задаёт нормативные контракты создания и редактирования корпуса, кабинета, предмета и проверки. Он также определяет общие правила ввода, безопасную обработку фотографий, формат ошибок API и требования к сообщениям на русском, казахском и английском языках.

Текущие демонстрационные поля `location`, `responsible`, `photoColor`, `displayStatus`, `price` и `quantity` не становятся обязательными доменными полями автоматически. Строковые `location` и `responsible` должны быть заменены ссылками и историческими снимками при миграции.

## Общие правила команд

- Сервер принимает JSON DTO с явным allowlist полей. Неизвестное поле возвращает issue `UNKNOWN_FIELD`.
- Связи передаются только непрозрачными ID. Название корпуса, кабинета или сотрудника не используется вместо ID.
- Создание и мобильные команды требуют `Idempotency-Key`.
- Изменение существующей записи требует положительную целочисленную `version`.
- Устаревшая версия возвращает `VERSION_CONFLICT`; сервер не выполняет частичное изменение.
- Пропущенное поле в PATCH означает «не изменять». `null` разрешён только для явно nullable-полей.
- Пустая строка необязательного текстового поля после нормализации сохраняется как `null`.
- Права, уникальность, версия, состояние связанных сущностей и аудит проверяются в одной транзакции.
- Клиент повторяет правила для быстрого UX, но сервер остаётся окончательным источником валидации.
- Любое текстовое значение хранится и отображается как plain text. HTML и Markdown не исполняются.

Обычный PATCH всегда использует envelope:

```json
{
  "version": 3,
  "changes": {
    "field": "value"
  }
}
```

`changes` должен содержать хотя бы одно разрешённое поле и не может содержать `id`, автора, audit-поля или серверные timestamps. Пустой PATCH и значение, совпадающее с текущим после нормализации, возвращают `VALIDATION_FAILED` с issue `NO_CHANGES`.

### Контракт идемпотентности

- Ключ содержит 16–128 ASCII-символов из `[A-Za-z0-9._:-]`; рекомендуется UUID/ULID, созданный клиентом для одной пользовательской команды.
- После успешной аутентификации отсутствие заголовка возвращает HTTP `400` и `IDEMPOTENCY_KEY_REQUIRED`, а неверная длина или символы — HTTP `400` и `IDEMPOTENCY_KEY_INVALID`. В обоих случаях `issues=[]`, `path` не используется и ключ не резервируется.
- Область уникальности: `(principalId, operationName, idempotencyKey)`. Ключ другого пользователя или другой операции не пересекается.
- После авторизации сервер строит fingerprint из имени операции, целевого ID и канонического нормализованного DTO, включая `version` и `photoUploadId`.
- Одинаковый ключ и fingerprint после завершённой команды возвращает тот же HTTP status и response body с `Idempotency-Replayed: true`; бизнес-операция, sequence, аудит и потребление upload повторно не выполняются.
- Одинаковый ключ с другим fingerprint возвращает HTTP `409` и `IDEMPOTENCY_CONFLICT`.
- Параллельный запрос с тем же ключом и fingerprint не начинает вторую транзакцию: он получает HTTP `409`, `IDEMPOTENCY_IN_PROGRESS` и `Retry-After`, а последующий retry воспроизводит результат первой команды.
- Проверка существующего idempotency record выполняется до проверки переданной `version`. Поэтому точный replay успешной команды работает, даже если версия объекта уже изменилась. Новый ключ со старой версией получает `VERSION_CONFLICT`.
- Успешные mutation records хранятся не меньше срока жизни объекта и не удаляются без сохранения эквивалентного уникального command reference в аудите. Детерминированные post-auth `4xx` хранятся 24 часа. Полностью откатившийся `5xx` не фиксируется как успех и допускает безопасный retry.
- Auth failure, rate limit и JSON, который нельзя разобрать, не резервируют ключ.

### Нормализация обычного текста

Эти правила не применяются к QR: QR использует отдельный алгоритм из `docs/qr-format.md`.

1. Принять только корректный Unicode без unpaired surrogate.
2. Привести строку к NFC.
3. Удалить с обоих краёв `U+0009`, `U+000A`, `U+000D` и `U+0020`.
4. Отклонить оставшиеся C0/C1 controls, `U+FEFF` и bidi controls, перечисленные в QR-спецификации.
5. Сохранить внутренние пробелы и регистр для отображения.
6. Считать длину в Unicode code points после нормализации.

Для поиска дублей создаётся отдельный comparison key: NFC, Unicode full case fold, удаление краевых пробелов и сведение последовательности внутренних ASCII-пробелов к одному. Исходное отображаемое значение не заменяется этим ключом.

## Корпус

### Создание

Техник и администратор могут создать корпус.

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `name` | Да | 2–120 code points после нормализации |
| `address` | Да | 5–300 code points после нормализации |
| `qrProvisioning` | Нет | По умолчанию `{ "mode": "generate" }`; допускается `{ "mode": "generate_with_legacy", "legacyValue": "..." }` |

Сервер задаёт `id`, `status=active`, `version=1`, автора и время создания. Объект всегда получает системный primary QR. Переданный legacy-код сохраняется отдельным alias по `docs/qr-format.md`.

Нормализованная пара `(nameKey, addressKey)` уникальна среди активных и архивных корпусов. Архивирование не освобождает имя для незаметного создания дубля.

### Редактирование

- Обычный PATCH доступен только администратору.
- Envelope содержит `version` и `changes`; allowlist `changes`: `name`, `address`.
- PATCH должен содержать хотя бы одно реальное изменение.
- QR меняется отдельной командой.
- Архивирование и восстановление выполняются отдельными командами с проверкой зависимостей.
- Техник после создания не редактирует корпус напрямую.

## Кабинет

### Создание

Техник и администратор могут создать кабинет внутри активного корпуса.

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `buildingId` | Да | Существующий активный корпус |
| `designation` | Да | Номер или название, 1–80 code points |
| `floorNumber` | Да | Целое число от `-5` до `200` |
| `floorLabel` | Нет | `null` либо 1–40 code points, например «Цоколь» |
| `qrProvisioning` | Нет | Те же варианты, что у корпуса |

Если `floorLabel` отсутствует, интерфейс строит локализованную подпись из `floorNumber`. Ответственного у кабинета нет.

Уникальна комбинация `(buildingId, floorNumber, designationKey)`. Одинаковые номера допустимы в разных корпусах и на разных этажах.

### Редактирование

- Обычный PATCH доступен только администратору.
- Envelope содержит `version` и `changes`; allowlist `changes`: `designation`, `floorNumber`, `floorLabel`.
- `buildingId` обычным PATCH не меняется; перенос кабинета является отдельной административной операцией.
- Нельзя архивировать корпус или кабинет с активными зависимостями без отдельного подтверждённого сценария.
- QR меняется отдельной командой.

## Предмет

### Создание

Техник и администратор могут создать предмет. Создание техником во время проверки дополнительно подчиняется правилам активной проверки.

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `name` | Да | 2–160 code points |
| `description` | Нет | `null` либо до 2000 code points |
| `roomId` | Да | Существующий активный кабинет |
| `inventoryNumber` | Да | `{ "kind": "official", "value": "..." }` либо `{ "kind": "temporary" }` |
| `photoUploadId` | Нет | Действующая загрузка текущего пользователя |
| `qrProvisioning` | Нет | `generate` либо `generate_with_legacy` |

Серверные значения при создании:

- `status=active`;
- `responsibleId=null`;
- `version=1`;
- системный primary QR;
- автор и время создания.

`category` пока nullable: обязательный справочник категорий не согласован в PRD. Демо-поля цены, количества, цвета и display status не входят в команду создания.

Техник не может передать в DTO `status`, `responsibleId`, произвольный primary QR или скрытую историю. Такие поля возвращают `NOT_ALLOWED`, а не игнорируются.

### Официальный инвентарный номер

- длина 1–64 code points;
- после общей нормализации первый и последний символ являются Unicode-буквой или цифрой;
- разрешены Unicode-буквы, Unicode-цифры, ASCII-пробел и символы `.`, `/`, `_`, `-`, `№`;
- запрещены пустое значение, `-`, `??`, значения с регистронезависимым ASCII-началом `YUQ`, голый 26-символьный системный токен и регистронезависимый шаблон `TMP-YYYY-<цифры>`;
- отображение сохраняет нормализованное написание;
- уникальность проверяется по отдельному NFC + full case fold ключу;
- проверка конфликтов с QR aliases выполняется по правилам `docs/qr-format.md`;
- номер архивного предмета, исторический номер и QR alias не могут быть незаметно переиспользованы другим предметом.

Legacy resolver продолжает использовать точное отображаемое значение. Если напечатанное legacy-значение отличается регистром, оно должно быть зарегистрировано как точный alias.

### Временный инвентарный номер

- создаётся только сервером;
- формат: `TMP-YYYY-NNNNNN`, цифровая часть может расти длиннее шести знаков;
- год определяется в бизнес-таймзоне `Asia/Aqtau`;
- sequence выдаётся транзакционно, номер уникален и никогда не переиспользуется;
- повтор команды с тем же `Idempotency-Key` возвращает тот же предмет и номер;
- предмет получает `numberState=temporary` и `needsOfficialNumber=true`;
- при назначении официального номера TMP остаётся в истории и не может быть выдан другому предмету.

### Создание внутри проверки

Одна транзакция должна:

1. Проверить, что проверка имеет статус `draft` и принадлежит технику, либо команда администратора содержит обязательный `reason`.
2. Проверить, что `roomId` является текущим кабинетом проверки.
3. Создать предмет, системный QR и допустимый legacy alias.
4. Создать аудит.
5. Создать единственный результат этого предмета в проверке.

Новый предмет считается проблемным результатом, даже если физически находится на месте. Ошибка любого шага откатывает всю транзакцию.

Команда использует один `Idempotency-Key` и точный DTO:

```json
{
  "inspectionId": "opaque-inspection-id",
  "inspectionVersion": 4,
  "roomId": "opaque-room-id",
  "item": {
    "name": "Неучтённый монитор",
    "description": null,
    "inventoryNumber": {
      "kind": "temporary"
    },
    "photoUploadId": "optional-upload-id",
    "qrProvisioning": {
      "mode": "generate_with_legacy",
      "legacyValue": "legacy-scanned-value"
    }
  },
  "result": {
    "result": "present",
    "comment": "Обнаружен во время обхода",
    "photoUploadId": "optional-result-upload-id"
  }
}
```

`roomId` предмета и `observedRoomId` результата берутся из верхнего уровня и не дублируются во вложенных DTO. `itemId` до транзакции отсутствует и возвращается в успешном ответе. Для нового предмета допустимы результаты `present`, `broken`, `undetermined`; `missing` и `moved` отклоняются как `WRONG_CONTEXT`.

Техник использует DTO как показано. Администратор добавляет верхнеуровневый `reason` длиной 1–1000 code points при выполнении команды в чужой проверке.

### Редактирование

| Поле/действие | Техник | Сотрудник | Администратор |
| --- | --- | --- | --- |
| `name`, `description` | Да | Нет | Да |
| Добавить/заменить/удалить фото | Да | Нет | Да |
| Официальный номер | Нет | Нет | Да |
| `roomId` | Нет | Нет | Да |
| Lifecycle status | Нет | Нет | Да |
| QR | Нет | Нет | Отдельная команда |
| Ответственный | Нет | Только принятие/передача | Передача или исключение с причиной |

Любое редактирование требует `version`. Изменение официального номера сохраняет прежнее значение в истории/alias. Изменение `roomId` администратором не стирает историю перемещений и не подменяет наблюдаемую локацию результатов проверки.

### DTO изменения предмета

Технический PATCH техника:

```json
{
  "version": 3,
  "changes": {
    "name": "Моноблок",
    "description": "Рабочее место преподавателя",
    "photo": {
      "action": "replace",
      "uploadId": "opaque-upload-id"
    }
  }
}
```

Allowlist `changes`: `name`, `description`, `photo`. Для `photo` допустимы ровно две формы:

```json
{ "action": "replace", "uploadId": "opaque-upload-id" }
```

```json
{ "action": "remove" }
```

Административный PATCH использует ту же форму и дополнительно допускает `roomId`. Изменение `roomId` требует `reason` длиной 1–1000 code points на верхнем уровне команды. Lifecycle status и инвентарный номер не входят в PATCH.

Официальный номер назначается отдельной командой администратора:

```json
{
  "itemId": "opaque-item-id",
  "version": 3,
  "officialNumber": "2416/1038",
  "reason": "Получен номер бухгалтерского учёта"
}
```

Команда применяется и к временному, и к ранее официальному номеру; `reason` обязателен, прежний номер сохраняется в истории и проходит проверку QR namespaces.

Lifecycle status меняется отдельной командой:

```json
{
  "itemId": "opaque-item-id",
  "version": 3,
  "status": "maintenance",
  "reason": "Передан в ремонт"
}
```

Допустимые статусы: `active`, `maintenance`, `decommissioned`. Допустимые переходы: `active ↔ maintenance`, `active|maintenance → decommissioned`. Восстановление из `decommissioned` выполняется отдельной административной командой с обязательной причиной. Архивирование не является lifecycle status и выполняется отдельно. Сотрудник и техник не могут вызывать эти команды.

### Команды ответственности

Все команды требуют `Idempotency-Key`; ответственность и версия предмета меняются в одной транзакции с аудитом.

Принятие свободного предмета сотрудником:

```json
{
  "itemId": "opaque-item-id",
  "itemVersion": 5
}
```

Сервер требует `status=active`, `responsibleId=null` и отсутствие активной передачи. Пользователь из сессии становится ответственным; передать чужой `employeeId` нельзя. При гонке выигрывает одна транзакция, остальные получают `ITEM_ALREADY_ASSIGNED`.

Запрос передачи занятого предмета:

```json
{
  "itemId": "opaque-item-id",
  "itemVersion": 5
}
```

Инициатор-сотрудник становится `proposedResponsibleId`, его согласие фиксируется самим запросом. Текущий ответственный сохраняется до завершения. Разрешён один активный запрос на предмет; второй получает `ACTIVE_TRANSFER_EXISTS`.

Решение текущего ответственного:

```json
{
  "transferId": "opaque-transfer-id",
  "version": 1,
  "action": "confirm"
}
```

Для `action=reject` обязателен `comment` длиной 1–1000 code points. Только сохранённый текущий ответственный может подтвердить или отклонить запрос. `confirm` атомарно меняет ответственного и версии; `reject` закрывает передачу без изменения предмета.

Новый ответственный может отменить ожидающий запрос командой `{ transferId, version }`. Другой сотрудник получает `TRANSFER_NOT_PARTICIPANT`.

Административное исключение:

```json
{
  "itemId": "opaque-item-id",
  "itemVersion": 5,
  "newResponsibleId": "opaque-user-id-or-null",
  "reason": "Прежний ответственный уволен"
}
```

Администратор может назначить сотрудника либо освободить предмет. Активная передача закрывается как `overridden`, всем участникам отправляется уведомление. `newResponsibleId` должен быть активным пользователем роли `employee`; причина 1–1000 обязательна.

Transfer status: `pending_current_owner`, `confirmed`, `rejected`, `cancelled`, `overridden`. Завершённую передачу нельзя открыть заново или изменить обычным PATCH.

## Фотографии

Фото необязательно для предмета, результата проверки и спора.

- Допустимы JPEG, PNG и WebP.
- SVG, GIF и другие исполняемые/анимированные форматы отклоняются.
- Максимум 10 MiB, 20 мегапикселей и 8192 px по любой стороне.
- Сервер проверяет magic bytes и полностью декодирует изображение; MIME и имя файла клиента не считаются доверенными.
- Публичная/интерфейсная копия создаётся повторным кодированием и не содержит EXIF, GPS и других исходных метаданных.
- Оригинал хранится в закрытом объектном хранилище и выдаётся только авторизованной серверной операцией с аудитом.
- `photoUploadId` принадлежит текущему пользователю, имеет TTL и потребляется одной успешной командой.
- Повтор с тем же `Idempotency-Key` не должен ошибочно считать уже потреблённую загрузку чужой.

Lifecycle загрузки:

- upload reservation действует 30 минут;
- неиспользованный бинарный объект после истечения reservation недоступен и удаляется background-задачей не позднее 24 часов;
- успешное присоединение атомарно переводит upload в `attached`; один upload нельзя присоединить к двум разным полям;
- замена создаёт новую текущую фотографию, а прежнюю помечает `superseded`;
- удаление убирает текущую ссылку, но не стирает audit metadata;
- superseded/removed фото карточки предмета хранится 90 дней, затем бинарный объект удаляется, а метаданные и аудит остаются;
- фото результата проверки и спора является evidence и хранится до архивирования проверки и окончания `EVIDENCE_RETENTION_DAYS`; production-конфигурация обязательна, минимум 365 дней, при отсутствии значения приложение не запускает purge; обычное редактирование предмета evidence не удаляет;
- административное досрочное удаление evidence требует отдельного разрешения, причины и аудита;
- при удалении бинарного объекта все ещё действующие signed URLs перестают обслуживаться серверным proxy либо истекают не позднее пяти минут.

### Доступ к фотографиям

Доступ наследуется от родительской сущности и проверяется при каждом запросе:

| Фото | Интерфейсная копия | Оригинал |
| --- | --- | --- |
| Предмет | Администратор; техник в разрешённом реестре/проверке; текущий ответственный; сотрудник при разрешённом сканировании активного предмета | Администратор и загрузивший пользователь |
| Результат проверки | Администратор; автор проверки; ответственный, сохранённый в результате | Администратор и загрузивший техник |
| Спор | Администратор; автор проверки; адресат решения/автор спора | Администратор и загрузивший сотрудник |

Роль `owner` не получает доступа QR-инвентаризации. URL выдаётся сервером после проверки parent access, действует не более пяти минут и не раскрывает путь хранилища. Знание `photoId` или URL после истечения срока не даёт доступ. Удаление доступа к родительской сущности немедленно блокирует выдачу нового URL.

## Проверка

### Создание и редактирование

Команда создания принимает только:

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `name` | Да | 2–120 code points |

Сервер задаёт `createdBy`, `status=draft`, даты и `version=1`. Имена проверок могут повторяться. Поля ответственного проверки, корпуса или кабинета в create DTO запрещены.

Техник создаёт проверку для себя. Администратор использует отдельную форму `{ name, technicianId }`, где `technicianId` указывает на активного пользователя роли `warehouse`; назначение сотрудника, подтверждающего всю проверку, отсутствует.

Автор-техник может менять только `name` собственного черновика. Обычный PATCH завершённой проверки запрещён. Администраторское вмешательство выполняется отдельной командой с обязательной причиной.

PATCH собственного черновика имеет envelope `{ version, changes: { name } }`; других полей в `changes` нет. Администратор изменяет имя чужой проверки отдельной командой `{ inspectionId, version, name, reason }`.

Статусы проверки:

```text
draft → awaiting_decisions → confirmed
   ├────────────────────────→ confirmed
   └────────────────────────→ cancelled
```

- `draft` — техник добавляет кабинеты и результаты.
- `awaiting_decisions` — обход завершён, обычное редактирование заблокировано, остаются проблемные решения.
- `confirmed` — проблем нет либо все решения подтверждены, исправлены или разрешены администратором.
- `cancelled` — незавершённый черновик отменён; результаты остаются только для аудита и не участвуют в отчётах завершённых проверок.
- Обратного перехода всей проверки в `draft` нет. Оспоренный результат пересматривается отдельной командой.

Отмена доступна только из `draft`. Автор-техник вызывает `{ inspectionId, version, reason }`, где `reason` содержит 1–1000 code points; администратор использует тот же DTO для любой черновой проверки. Команда требует `Idempotency-Key`, атомарно задаёт `status=cancelled`, `cancelledAt`, `cancelledBy`, сохраняет причину и аудит. Она не удаляет созданные во время проверки предметы и не откатывает их инвентарные номера/QR; комнаты, snapshots и результаты становятся read-only audit data. Решения ещё не создавались, поэтому cleanup решений не выполняется. Из `awaiting_decisions`, `confirmed` и `cancelled` команда возвращает `INVALID_STATE`.

Проверка является агрегатом конкурентности. Любая команда, меняющая `draft` — переименование, добавление/завершение кабинета, создание предмета внутри проверки, создание/PATCH результата, отмена или завершение — сначала берёт write lock строки проверки, затем проверяет `status=draft` и переданную версию агрегата, выполняет всю операцию и увеличивает `inspection.version` в той же транзакции. Поэтому отмена/завершение не могут обогнать незавершённое изменение результата, а draft-мутация не может закоммититься после них. Для команд, меняющих дочернюю запись, клиент передаёт и `inspectionVersion`, и собственную `version` дочерней записи; конфликт любой из них откатывает команду целиком.

### Добавление кабинета

Кабинет добавляется отдельной командой:

```json
{
  "inspectionId": "opaque-id",
  "buildingId": "opaque-id",
  "roomId": "opaque-id",
  "version": 1
}
```

Сервер проверяет, что кабинет активен и принадлежит указанному корпусу. При первом включении сохраняются снимки корпуса, кабинета и исходного набора предметов. Повторное добавление того же кабинета идемпотентно и не обновляет исходный снимок.

Команду выполняет автор-техник собственной проверки. Администратор может добавить кабинет в любую проверку, передав обязательный `reason`; это не меняет назначенного `technicianId`.

Кабинет без исходных предметов допустим, но техник должен явно завершить его осмотр. Это отличает проверенный пустой кабинет от кабинета, который только открыли.

Команда завершения осмотра кабинета:

```json
{
  "inspectionId": "opaque-inspection-id",
  "roomId": "opaque-room-id",
  "version": 4
}
```

Её вызывает автор-техник для собственного `draft`. Администратор может выполнить команду для любой проверки, добавив `reason` длиной 1–1000 code points; вмешательство записывается в аудит. Сервер проверяет результаты всех предметов исходного снимка, после чего сохраняет `inspectedAt` и `inspectedBy`. Повтор с тем же idempotency key воспроизводит ответ. Новая команда для уже осмотренного кабинета возвращает текущее состояние без изменения снимка.

### Результат предмета

| Поле | Обязательность | Правило |
| --- | --- | --- |
| `inspectionId` | Да | Собственный активный черновик техника |
| `inspectionVersion` | Да | Положительная версия draft-агрегата проверки |
| `itemId` | Да | Существующий предмет либо предмет, создаваемый атомарно |
| `observedRoomId` | Да | Текущий кабинет проверки |
| `result` | Да | `present`, `missing`, `moved`, `broken`, `undetermined` |
| `comment` | Нет | `null` либо до 1000 code points |
| `photoUploadId` | Нет | Действующая загрузка |
| `version` | Для изменения | Версия существующего результата |

Сервер сохраняет `registryRoomIdAtScan`, `observedRoomId`, `responsibleIdAtScan`, снимки предмета/кабинета/корпуса, автора, время и версию результата.

Обязательные cross-field правила:

- уникальность `(inspectionId, itemId)`;
- `missing` создаётся только для предмета исходного снимка выбранного кабинета;
- `moved` не меняет `roomId` предмета в реестре;
- предмет из другого кабинета может получить `moved` либо другой явно выбранный техником результат после предупреждения;
- повторное сканирование открывает существующий результат;
- изменение результата создаёт audit revision;
- спор ответственного требует комментарий 1–1000 code points;
- административное разрешение требует причину 1–1000 code points.

Создание результата принимает все поля таблицы, кроме `version`. После создания `inspectionId` и `itemId` неизменяемы.

Обычный PATCH результата в `draft`:

```json
{
  "resultId": "opaque-result-id",
  "inspectionVersion": 7,
  "version": 2,
  "changes": {
    "observedRoomId": "opaque-room-id",
    "result": "moved",
    "comment": "Найден в соседнем кабинете",
    "photo": {
      "action": "replace",
      "uploadId": "opaque-upload-id"
    }
  }
}
```

Allowlist `changes`: `observedRoomId`, `result`, `comment`, `photo`. `inspectionVersion` и версия результата `version` находятся только на верхнем уровне. `inspectionId`, `itemId`, первоначальный `responsibleIdAtScan` и исходные snapshots неизменяемы. Для `photo` используются формы `replace/remove`, описанные для предмета.

После завершения проверки автор-техник может изменить только оспоренный результат командой повторной проверки с тем же allowlist. Создаётся новая revision, а первоначальный `responsibleIdAtScan` сохраняется для всего жизненного цикла результата: последующая передача предмета не меняет адресата этого решения.

При любой повторной проверке прежнее `disputed` решение атомарно помечается `superseded`. Если результат меняется на `present`, новое подтверждение не требуется. Если результат остаётся проблемным, создаётся новая `pending` revision решения для того же `responsibleIdAtScan`. Если ответственного на момент первого сканирования не было, решение сохраняет `recipientKind=admin_queue` и `recipientId=null`.

Создание и изменение результата выполняет автор-техник. Администратор может выполнить ту же операцию для любой проверки, добавив `reason` длиной 1–1000 code points на верхнем уровне команды; все остальные allowlists и инварианты сохраняются.

### Завершение

Завершение разрешено, если:

- в проверку включён хотя бы один кабинет;
- каждый кабинет явно отмечен осмотренным;
- каждый предмет исходного снимка имеет результат;
- каждый созданный внутри проверки предмет имеет ровно один результат;
- нет незавершённой атомарной операции или конфликта версии.

Переход статуса проверки и создание решений по проблемным результатам выполняются одной транзакцией.

Команда завершения проверки:

```json
{
  "inspectionId": "opaque-inspection-id",
  "version": 7
}
```

Её вызывает автор-техник для собственного `draft`. Администратор может завершить любую проверку с обязательным `reason`, но административное право не обходит ни одно из перечисленных условий завершения. Команда требует `Idempotency-Key`; неверное исходное состояние возвращает `INVALID_STATE`. При отсутствии проблемных результатов сервер атомарно устанавливает `confirmed` и `confirmedAt`. При наличии `missing`, `moved`, `broken`, `undetermined` или нового предмета сервер устанавливает `awaiting_decisions` и создаёт по одному pending decision на актуальную revision каждого проблемного результата.

Decision state: `pending`, `confirmed`, `disputed`, `superseded`, `resolved_by_admin`.

Каждое решение содержит `recipientKind=user|admin_queue` и nullable `recipientId`. При наличии `responsibleIdAtScan` сервер записывает `recipientKind=user` и тот же ID в `recipientId`. При `responsibleIdAtScan=null`, в том числе для нового предмета, сервер записывает `recipientKind=admin_queue`, `recipientId=null`: решение появляется в общей очереди всех активных администраторов, а личное `confirm/dispute` для него недоступно. Любой активный администратор закрывает такое решение административной командой ниже; `version` и row lock гарантируют ровно одного победителя, остальные получают `VERSION_CONFLICT`. Назначать случайного администратора или менять recipient после создания нельзя.

Команды адресата решения:

```json
{
  "decisionId": "opaque-decision-id",
  "version": 1,
  "action": "confirm"
}
```

```json
{
  "decisionId": "opaque-decision-id",
  "version": 1,
  "action": "dispute",
  "comment": "Предмет находится на рабочем месте",
  "photoUploadId": "optional-upload-id"
}
```

`confirm` и `dispute` доступны только сохранённому `recipientId` решения с `recipientKind=user`; для `dispute` комментарий обязателен. Административное разрешение решения любого типа, включая `admin_queue`, использует отдельную команду `{ decisionId, version, resolution, reason }`, где `reason` обязателен, а `resolution` принимает:

- `confirm_result` — сохранить текущий проблемный результат и считать решение подтверждённым администратором;
- `dismiss_to_present` — создать аудированную revision результата `present` и закрыть решение.

Каждая команда `confirm`, `dispute`, административного разрешения и повторной проверки сначала берёт write lock родительской проверки, затем проверяет version/состояние решения и изменяет его. Таким образом, переходы разных решений одной проверки сериализованы. После изменения сервер в той же транзакции и под тем же lock проверяет все актуальные decisions. Когда `pending`/`disputed` решений не остаётся, условное обновление `inspection.status=awaiting_decisions` атомарно устанавливает `confirmed` и `confirmedAt`. Конкурентная команда после получения lock видит уже актуальные решения/статус и либо завершает оставшееся действие, либо возвращает `VERSION_CONFLICT`/`INVALID_STATE`; проверка не может навсегда остаться в `awaiting_decisions` из-за lost wake-up.

## Формат ошибок API

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "issues": [
      {
        "path": "inventoryNumber.value",
        "code": "RESERVED_VALUE",
        "params": {
          "namespace": "TMP"
        }
      }
    ],
    "requestId": "opaque-id"
  }
}
```

- `code` и issue codes являются стабильным контрактом.
- `path` использует только заранее известное имя поля DTO; для общих ошибок применяется пустая строка. Для `UNKNOWN_FIELD` сервер возвращает безопасный `path="body"` и не отражает присланное имя поля ни в `path`, ни в `params`.
- `params` содержит только безопасные числа или enum, никогда исходный пользовательский текст.
- `requestId` не содержит данные пользователя.
- Сервер не возвращает локализованный текст и не отражает сырой payload.
- Несколько независимых ошибок возвращаются вместе в детерминированном порядке полей.
- Порядок проверки: transport size/media type/rate limit → JSON parse → authentication и route authorization → наличие/синтаксис `Idempotency-Key` для соответствующей команды → DTO allowlist/type/field validation → поиск idempotency record → version/domain constraints. Поэтому malformed JSON имеет приоритет над отсутствующим ключом, а `UNAUTHENTICATED` не раскрывает требования защищённой команды.

### Верхнеуровневые коды

`INVALID_JSON`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `VALIDATION_FAILED`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `NOT_ACCESSIBLE`, `DUPLICATE_BUILDING`, `DUPLICATE_ROOM`, `DUPLICATE_INVENTORY_NUMBER`, QR-коды из `docs/qr-format.md`, `WRONG_CONTEXT`, `VERSION_CONFLICT`, `IDEMPOTENCY_KEY_REQUIRED`, `IDEMPOTENCY_KEY_INVALID`, `IDEMPOTENCY_CONFLICT`, `IDEMPOTENCY_IN_PROGRESS`, `INVALID_STATE`, `ITEM_ALREADY_ASSIGNED`, `ACTIVE_TRANSFER_EXISTS`, `TRANSFER_NOT_PARTICIPANT`, `PHOTO_TOO_LARGE`, `PHOTO_UNSUPPORTED`, `PHOTO_INVALID`, `RATE_LIMITED`, `INTERNAL_ERROR`.

`PAYLOAD_TOO_LARGE` с `issues=[]` применяется к общему превышению лимита HTTP request body до разбора JSON. `UNSUPPORTED_MEDIA_TYPE` с `issues=[]` применяется, когда JSON-route получает Content-Type не `application/json`. Для upload-route сохраняются более конкретные `PHOTO_TOO_LARGE` и `PHOTO_UNSUPPORTED`.

### Field issue codes

`REQUIRED`, `INVALID_TYPE`, `TOO_SHORT`, `TOO_LONG`, `INVALID_FORMAT`, `OUT_OF_RANGE`, `RESERVED_VALUE`, `UNKNOWN_FIELD`, `NOT_ALLOWED`, `NO_CHANGES`, `RELATION_NOT_FOUND`, `RELATION_INACTIVE`.

### HTTP status

| HTTP | Применение |
| --- | --- |
| `400` | Неправильный JSON или структура запроса, которую нельзя разобрать |
| `401` | Нет действующей сессии |
| `403` | Роль не имеет права на операцию |
| `404` | Объект не найден либо скрыт правилом non-enumeration |
| `409` | Дубль, конфликт версии/idempotency или недопустимый переход состояния |
| `413` | `PAYLOAD_TOO_LARGE` для общего request body; `PHOTO_TOO_LARGE` для фото |
| `415` | `UNSUPPORTED_MEDIA_TYPE` для JSON-route; `PHOTO_UNSUPPORTED` для upload-route |
| `422` | Поля разобраны, но не прошли field/domain validation |
| `429` | Превышен лимит запросов |
| `500` | Неожиданная ошибка; детали скрыты, возвращается `requestId` |

UX ошибок:

- значения формы сохраняются после ошибки;
- рядом с полем показывается конкретное сообщение;
- поле получает `aria-invalid=true` и связь через `aria-describedby`;
- после submit фокус переходит к первой ошибке;
- общий summary имеет `role="alert"`;
- конфликт версии предлагает обновить данные, а не молча перезаписывает их.

## Приёмочные критерии

- Все create/PATCH DTO имеют allowlist, обязательность, длины и conditional rules.
- Сервер запрещает mass assignment скрытых полей.
- DB constraints обеспечивают уникальность QR, официального номера, корпуса/кабинета и результата предмета.
- Техник не может прямым запросом изменить QR, номер, локацию, status или ответственность.
- Повтор idempotent-команды создаёт ровно один объект и один TMP/QR.
- Фото проходит реальное декодирование и недоступно без авторизации.
- Проверка использует исходный снимок кабинета и не зависит от последующих перемещений в реестре.
- Ошибка имеет стабильный machine code, безопасные params и перевод ru/kk/en.
- Sensitive и административные изменения аудируются в той же транзакции.

## Минимальная тестовая матрица реализации

| Область | Обязательные случаи |
| --- | --- |
| Тексты | Пусто, только пробелы, min/max ±1, ru/kk/en, emoji, combining chars, NUL, bidi, BOM, unpaired surrogate |
| Корпус | Валидное создание, duplicate pair, QR conflict, редактирование техником запрещено |
| Кабинет | Неверный/inactive корпус, floor границы, label, дубль в том же и другом корпусе |
| Номер | Ведущие нули, `/`, `-`, Unicode, case conflict, `-`, `??`, `YUQ`, bare token, TMP spoofing |
| TMP | Смена года в Asia/Aqtau, параллельная генерация, retry, rollback без частичного объекта |
| Идемпотентность | Валидность ключа, тот же/другой fingerprint, concurrent in-progress, replay после смены version, TTL 4xx, rollback 5xx |
| Предмет | Official/temporary ветки, inactive room, PATCH allowlist, photo remove/replace, number/status commands, mass assignment, admin room change, stale version |
| Ответственность | Concurrent accept, один active transfer, requester/current-owner permissions, reject comment, cancel, admin override/reason, notification/audit rollback |
| QR | Generated, valid legacy, duplicate, ambiguous, revoked, unissued system code, atomic alias change |
| Фото | MIME spoof, SVG, oversized bytes/pixels, corrupt/truncated, EXIF/GPS stripping, expired/foreign upload, parent-based access, original vs derivative |
| Проверка | Только name при создании, повторяющиеся имена, запрет ответственного, draft/completed edit |
| Результат | Create/update allowlists, inspection/result versions, immutable IDs/snapshots/recipient, все пять enum, missing без scan, wrong room, moved без изменения реестра, duplicate scan |
| Завершение | Mark-room permission/DTO, необработанный baseline item, пустой кабинет, новый предмет, concurrent result mutation, aggregate lock, atomic decisions/status, admin без обхода prerequisites, отмена draft и неизменность созданных предметов |
| Решения | Confirm/dispute/admin DTO, обязательный comment/reason, user recipient, admin queue без случайного адресата, superseded revision, concurrent admin resolution, сериализация разных решений одной проверки, auto-confirm без lost wake-up |
| Ошибки/i18n | Одинаковые codes во всех языках, наличие ключей ru/kk/en, fallback, focus/ARIA, отсутствие raw payload |
| Безопасность | 401/403/404 non-enumeration, прямое повышение прав, stale version, audit rollback |
