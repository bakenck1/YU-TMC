# Отдельный API материалов 1С

Адрес после развёртывания: `https://inventory.yu.edu.kz/api/integrations/1c/materials`.
Основные средства продолжают отправляться на прежний `/api/integrations/1c/fixed-assets`.
Принадлежность к материалам определяется отдельным каналом выгрузки, а не названием,
префиксом инвентарного номера или наличием штрихкода.

## Запрос

Готовый пример: [one-c-materials.xml](examples/one-c-materials.xml).
Перед реальной отправкой замените дату среза и данные на значения вашей базы.
Для выгрузки по МОЛ передавайте `SchemaVersion=2`. В XML-примере ФИО и коды МОЛ
условные: замените их настоящими GUID/устойчивыми кодами 1С. Не используйте номер
строки, случайный GUID или идентификатор, вычисленный из ФИО.

```http
POST /api/integrations/1c/materials
Authorization: Bearer <ключ материалов>
Content-Type: application/xml; charset=utf-8
X-Source-Filename: materials_20261014.xml
```

Ключ берётся из `ONE_C_MATERIALS_API_KEY`. Настройки и ключ ОС не изменяются.
`X-Source-Filename` необязателен; это имя файла без пути. Кодировка — UTF-8.
Допускается также `text/xml`. Размер до 64 МиБ, до 50 000 строк в одном запросе.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Materials>
  <SchemaVersion>2</SchemaVersion>
  <SnapshotAt>2026-10-14T12:00:00+05:00</SnapshotAt>
  <Material>
    <Code>00000006135</Code>
    <Name>МФУ Laser Jet M130</Name>
    <InventoryNumber>1350/14444</InventoryNumber>
    <AccountCode>1317</AccountCode>
    <Barcode/>
    <Unit>шт</Unit>
    <Quantity>1</Quantity>
    <UnitPrice>66784.48</UnitPrice>
    <WarehouseCode>WH-01</WarehouseCode>
    <WarehouseName>Основной склад</WarehouseName>
    <Responsible>Иванов Иван Иванович</Responsible>
    <ResponsibleCode>000001</ResponsibleCode>
    <ResponsibleGUID>eba5b834-db3b-11f0-a26e-7cc25579bdd7</ResponsibleGUID>
  </Material>
  <Material>
    <Code>00000006135</Code>
    <Name>МФУ Laser Jet M130</Name>
    <Unit>шт</Unit>
    <AccountCode>1317</AccountCode>
    <Quantity>2</Quantity>
    <UnitPrice>65000.00</UnitPrice>
    <WarehouseCode>WH-01</WarehouseCode>
    <WarehouseName>Основной склад</WarehouseName>
    <Responsible>Петров Пётр Петрович</Responsible>
    <ResponsibleCode>000002</ResponsibleCode>
  </Material>
</Materials>
```

Это две отдельные позиции одного материала на одном складе у разных МОЛ,
с независимыми количеством и ценой. Разные счета и склады также разделяются.
Склады 1С не становятся кабинетами Inventory автоматически.

Соответствие колонкам ведомости: «Номенклатура» → `Name`, «Счёт» → `AccountCode`,
«Субконто1Код» (код номенклатуры) → `Code`, единица измерения → `Unit`,
«МОЛ» → `Responsible`, учётная цена **за единицу** → `UnitPrice`, количество → `Quantity`.
Код номенклатуры не является инвентарным номером. Дату среза, код/GUID МОЛ и при
наличии идентификатор склада передавайте отдельными полями.

## Поля

| Поле | Обязательно | Назначение |
|---|---|---|
| `SchemaVersion` в корне | Да для нового формата | `2`. Отсутствие или `1` оставляет прежний формат материал/склад. |
| `SnapshotAt` в корне | Да | Дата среза всех строк, ISO 8601 с часовым поясом, например `2026-10-14T12:00:00+05:00`. |
| `Code` | Да | Устойчивый код материала, строка; сохраняются ведущие нули. Не меняйте его между выгрузками. |
| `Name` | Да | Исходное полное наименование, включая номер в описании, если он там хранится. |
| `AccountCode` | Да в версии 2 | Бухгалтерский счёт, например `1317`, строкой. Входит в ключ остатка. |
| `GUID` | Нет | GUID номенклатуры, если доступен в 1С. Не подставляйте сюда GUID основного средства. |
| `InventoryNumber` | Нет | Инвентарный номер отдельно от кода номенклатуры. |
| `Barcode` | Нет | Реальный штрихкод; отсутствие допускается. Не нужно генерировать его в 1С для этого запроса. |
| `Unit` | Нет | Единица измерения. Рекомендуется передавать. |
| `Quantity` | Да | Остаток на данном складе; до 3 знаков после запятой. Допускаются нулевые и отрицательные остатки для сверки. |
| `UnitPrice` | Нет | Учётная цена за единицу на данном складе, тенге; неотрицательная, до 2 знаков после запятой. |
| `Currency` | Нет | Только `KZT`; при отсутствии подразумевается `KZT`. |
| `WarehouseCode` | Условно | Устойчивый код склада. Предпочтительный идентификатор склада. |
| `WarehouseGUID` | Условно | GUID склада, если код склада отсутствует. |
| `WarehouseName` | Нет | Название склада для отображения; требует `WarehouseCode` или `WarehouseGUID`. |
| `Responsible` | Нет | ФИО ответственного за эту позицию материала на складе, если оно есть в 1С. |
| `ResponsibleGUID` | Нет | GUID ответственного в 1С, если доступен; корректный UUID. ФИО и GUID можно передавать независимо. |
| `ResponsibleCode` | Условно в версии 2 | Устойчивый код МОЛ из 1С, с ведущими нулями. Если МОЛ есть, нужен этот код или `ResponsibleGUID`. Код предпочтительнее, если оба доступны. |
| `ReplaceLegacyBalances` в корне | Нет | `true` только для согласованного перехода с общих остатков версии 1 на полные остатки по МОЛ версии 2. По умолчанию `false`. |

Если ответственный отсутствует, пропустите `Responsible`, `ResponsibleCode` и `ResponsibleGUID` или
передайте пустые теги. ФИО сохраняется без поиска сотрудника Inventory по имени;
автоматическое назначение или изменение ответственного карточки не выполняется.
В версии 2 код/GUID МОЛ входит в ключ остатка. ФИО служит только для отображения:
переименование при прежнем идентификаторе обновляет строку без дубликата.
Одинаковое ФИО у разных идентификаторов не объединяет остатки. ФИО без кода/GUID МОЛ
в версии 2 отклоняется. Не подставляйте одного фиктивного МОЛ для разных людей.
Если используете код МОЛ, не переключайтесь на один GUID в следующих выгрузках
без согласования переноса. Код МОЛ не должен указывать на разные GUID.
Текстовые поля ограничены 255 символами.
В версии 2 коды материала, склада, счёта и МОЛ ограничены дополнительно 128 байтами
UTF-8, без управляющих символов: составной ключ должен помещаться в индекс PostgreSQL.
Пустые поля ответственного в новом срезе
означают отсутствие сведений об ответственном, а не сохранение прежнего ФИО.

Цены и количество принимаются с точкой или десятичной запятой; научная запись
(`1e3`), `NaN`, бесконечность и значения вне допустимой точности отклоняются.
Пустая цена сохраняется как отсутствие значения, а `0` — как переданный ноль.
Учётная цена материала отличается от остаточной стоимости ОС.

Если склад не передаётся, все три поля склада должны быть пустыми или отсутствовать.
Такая позиция сохраняется как «склад не указан». В версии 2 допускаются разные
счета и разные МОЛ одного материала даже без склада; повтор полного ключа запрещён.
Раздельный учёт нескольких неизвестных складов невозможен.
При передаче нескольких складов их идентификаторы обязательны и должны оставаться
одинаковыми во всех последующих выгрузках. Не переключайте одну позицию с кода склада
на GUID или со «склад не указан» на конкретный склад без согласования переноса данных.

## Повторная выгрузка и хранение

- Ключ версии 2: точный код материала + идентификатор склада (код, иначе GUID) +
  счёт + идентификатор МОЛ (код, иначе GUID). Названия, цена и номер строки не
  являются идентификаторами. Ключ версии 1 остаётся прежним.
- Повтор одного ключа внутри XML отклоняет весь запрос; сначала агрегируйте остатки
  по полному ключу в 1С. Если другие измерения дают разные цены одного полного
  ключа, согласуйте их обработку перед выгрузкой. Не объединяйте строки разных МОЛ,
  счетов или складов и не усредняйте цены без согласования бухгалтерии.
- Приём атомарный: ошибка не сохраняет половину пакета.
- Новые позиции создаются, изменившиеся обновляются, одинаковые учитываются как
  `unchanged`. Повтор уже принятого файла не откатывает более новые остатки.
- Для нового файла дата среза не может быть старше последнего принятого пакета
  материалов. Выгружайте пакетами в порядке даты среза. Более старая дата также
  не может заменить более свежую позицию; разные данные
  одного ключа с той же датой среза вызывают конфликт. Для корректировки используйте
  новую дату среза.
- Строки, отсутствующие в новом пакете, сохраняются. Для обнуления ранее переданного
  остатка отправьте соответствующую позицию с `Quantity=0`. Выгрузка только ненулевых
  остатков без нулевых обновлений не позволяет узнавать о полностью израсходованных
  материалах. Это приём переданных позиций, без автоматического удаления пропущенных.
  При передаче от одного МОЛ другому отправляйте нулевой остаток прежнего МОЛ и
  новый остаток получателя; отсутствие прежнего МОЛ в пакете не обнуляет его.

### Переход со старого формата

Старые XML без `SchemaVersion` принимаются как версия 1, с прежними ключами и хешами.
`AccountCode` и `ResponsibleCode` в версии 1 не допускаются — нужен явный `SchemaVersion=2`.

Если по материалу/складу уже принят общий остаток версии 1, переход без явного
`ReplaceLegacyBalances=true` отклоняется (409). Флаг разрешайте только для полного
согласованного пакета: по каждому заменяемому материалу/складу нужны все счета и
все МОЛ, включая требуемые нулевые остатки. Дата среза должна быть новее общего
остатка. Сервер не может проверить полноту исходной базы 1С по самому XML.

При переходе общий остаток помечается `superseded_at`, не удаляется; история не
меняется. Текущие остатки выбирайте с `WHERE superseded_at IS NULL`. Не суммируйте
архивную общую строку с детализацией по МОЛ. Новая выгрузка версии 1 не может
вернуть общий остаток. Повтор старого принятого файла только возвращает прежний
ответ и не восстанавливает его. Если материалов ещё не выгружали, начните сразу
с версии 2 без флага перехода.

Данные хранятся отдельно от ОС в `yu_inventory.one_c_material_inbox`; история пакетов
и их строк — в `one_c_material_import_batches` и `one_c_material_import_batch_rows`.
API не создаёт физические карточки ТМЦ, не заменяет их фото, кабинеты и ответственных,
не изменяет цены существующих карточек Inventory. Такая публикация требует отдельного
сопоставления и подтверждения. Импорт Excel «материалы 2026.xls» остаётся независимым.

## Ответы

Успешный ответ — JSON, HTTP 200, со счётчиками `received`, `created`, `updated`,
`unchanged`, идентификатором партии `batchId` и идентификатором запроса `requestId`.
Поле `replayed=true` означает повтор уже принятого файла: возвращается его прежняя
партия, текущие остатки не перезаписываются, даже если после неё были более новые срезы.
Сумма трёх счётчиков равна `received`; в версии 2 это позиции материал/счёт/склад/МОЛ,
а не физические единицы или созданные карточки Inventory.

| HTTP | Значение |
|---|---|
| 200 | Пакет принят или уже был принят. |
| 400 | Некорректный XML, поле, повтор ключа или число. |
| 401 | Отсутствует или неверен ключ материалов. |
| 409 | Устаревший срез или конфликт данных на одну дату. |
| 413 | Превышен размер запроса. |
| 415 | Неподдерживаемый Content-Type. |
| 429 | Лимит запросов или параллельный импорт; повторить после `Retry-After`. |
| 503 | Ключ не настроен, БД недоступна или превышено время обработки. |

`GET /api/integrations/1c/materials` показывает возможности и факт настройки ключа;
это не выгрузка данных и не проверка доступности базы.

Для первой проверки отправьте 5–10 строк: материал на двух складах с разной ценой,
один материал у двух МОЛ на одном складе, разные счета, строку без штрихкода,
строку с пустой ценой, нулевой и дробный остаток. После успешного
приёма повторите тот же XML и проверьте `created=0`, `updated=0`, `unchanged=received`.

## Развёртывание

Перед запуском новой версии выполните резервное копирование и `npm run db:migrate -- --target=production`
с production-переменными окружения. Схема добавляется отдельной миграцией; существующий
API ОС не меняется. В закрытый `/etc/yu-inventory/yu-inventory.env` через `sudoedit`
добавьте `ONE_C_MATERIALS_API_KEY=<отдельный случайный ключ>`. Ключ можно сгенерировать
локально командой `openssl rand -hex 32`; передайте его программисту по закрытому каналу.
После успешной сборки перезапустите `yu-inventory`, проверьте GET нового адреса и пробный POST.
