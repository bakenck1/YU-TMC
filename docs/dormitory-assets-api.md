# API ТМЦ общежитий

Версия контракта: 1.0

API предназначен для `dormitory.yu.edu.kz` и отдаёт только ТМЦ, чьё текущее
местонахождение относится к одному из общежитий в справочнике YU Inventory.
Ключ каталога даёт только чтение и не открывает сотрудников, общий склад,
фотографии или административные методы. Создание заявок защищено отдельным
write-ключом.

## Авторизация

В окружении YU Inventory задаются отдельные секреты:

```env
DORMITORY_API_KEY=<случайный секрет не короче 32 байт>
DORMITORY_API_KEY_NEXT=
DORMITORY_WRITE_API_KEY=<отдельный случайный секрет не короче 32 байт>
DORMITORY_WRITE_API_KEY_NEXT=
```

Клиент передаёт ключ только в заголовке:

```http
Authorization: Bearer <DORMITORY_API_KEY>
```

Проверка подключения:

```http
GET https://inventory.yu.edu.kz/api/v1/dormitory/auth/check
```

Успешный ответ: `{"valid":true,"scope":"dormitory-assets:read"}`.

## Получение ТМЦ

```http
GET https://inventory.yu.edu.kz/api/v1/dormitory/items?limit=100
Authorization: Bearer <DORMITORY_API_KEY>
```

`limit` необязателен: по умолчанию `100`, допустимо от `1` до `200`. Если
`nextCursor` не равен `null`, следующая страница запрашивается с теми же
параметрами и `cursor=<nextCursor>`. Курсор непрозрачный: клиент не должен его
разбирать или изменять.

Пример ответа:

```json
{
  "items": [
    {
      "id": "00000000-0000-4000-8000-000000000021",
      "code": "000009352",
      "inventoryNumber": "INV-9352",
      "name": "Кровать",
      "category": "Мебель",
      "acceptanceDate": "2025-11-20",
      "responsiblePerson": "Иванов Иван Иванович",
      "department": "Студенческий кампус",
      "location": {
        "buildingId": "00000000-0000-4000-8000-000000000010",
        "buildingName": "Общежитие 3",
        "roomId": "00000000-0000-4000-8000-000000000011",
        "room": "205",
        "floorNumber": 2
      },
      "initialCost": 50000,
      "residualCost": 30000,
      "currency": "KZT",
      "status": "active",
      "condition": "good",
      "accountingStatus": "Принято к учёту",
      "updatedAt": "2026-09-22T08:00:00.000Z"
    }
  ],
  "nextCursor": null
}
```

`initialCost`, `acceptanceDate`, `category`, `residualCost` и
`accountingStatus` берутся из связанной выгрузки 1С, когда она есть. Для старых
или созданных вручную карточек API использует цену и категорию из YU Inventory;
неизвестные бухгалтерские значения возвращаются как `null`.

## Статусы и повреждения

- `status=active` — предмет используется;
- `status=maintenance` — предмет передан на ремонт или ожидает решения;
- `status=written_off` — списание уже подтверждено в YU Inventory;
- `condition=damaged` — зафиксировано повреждение, но это само по себе ещё не
  означает бухгалтерское списание.

## Передача заявки комендантом

Когда комендант выбирает действие для ТМЦ, система общежития отправляет:

```http
POST https://inventory.yu.edu.kz/api/v1/dormitory/requests
Authorization: Bearer <DORMITORY_WRITE_API_KEY>
Content-Type: application/json

{
  "externalRequestId": "dormitory-3-2026-00042",
  "itemId": "00000000-0000-4000-8000-000000000021",
  "action": "repair",
  "description": "Необходимо отремонтировать ножку кровати",
  "reporterName": "Комендант общежития 3"
}
```

Допустимые действия: `repair`, `damaged`, `missing`, `other`.
`externalRequestId` должен быть постоянным уникальным идентификатором заявки в
системе общежития. Повтор того же запроса безопасен и не создаёт дубликат;
повторное использование идентификатора с другим содержимым возвращает `409`.

После принятия запроса YU Inventory атомарно:

1. проверяет, что ТМЦ действительно находится в общежитии и не списан;
2. создаёт запись в общем разделе «Заявки»;
3. переводит ТМЦ в `maintenance`;
4. ставит `needs_attention` для ремонта/прочего либо `damaged` для повреждения/утраты;
5. записывает аудит и отправляет push-уведомление администраторам.

Ключ записи отделён от ключа чтения: утечка `DORMITORY_API_KEY` не позволяет
создавать заявки или менять состояние ТМЦ.

При повреждении система общежития не должна автоматически ставить
`written_off`. Правильный процесс: зарегистрировать инцидент и студента,
зафиксировать фото и сумму, перевести ТМЦ в `maintenance`, затем сотрудник
выбирает ремонт, возврат в эксплуатацию или списание. Удержание депозита и
бухгалтерское списание — разные решения и должны иметь отдельные подтверждения.

Ответы API имеют `Cache-Control: private, no-store` и `X-Request-Id`. Возможные
ошибки: `400 INVALID_PAGE`, `401 UNAUTHORIZED`, `503 API_NOT_CONFIGURED` и
`503 DEPENDENCY_UNAVAILABLE`.

## Ротация ключа

Новый ключ сначала записывают в `DORMITORY_API_KEY_NEXT`, перезапускают
приложение и проверяют оба ключа. После перевода клиента новый ключ переносят в
`DORMITORY_API_KEY`, очищают `DORMITORY_API_KEY_NEXT` и снова перезапускают
приложение. Ключ нельзя передавать в URL, Git или журналы.

Ключ записи ротируется тем же способом через `DORMITORY_WRITE_API_KEY_NEXT`, но
никогда не должен совпадать с ключом чтения.
