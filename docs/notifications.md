# Уведомления первой версии

## Решение по каналам

В первой версии используется только постоянный внутренний канал приложения:

- центр уведомлений;
- счётчик непрочитанных;
- ссылки на доступное пользователю действие;
- отдельные рабочие очереди передач и решений.

Web push и email не входят в первую версию. Они подключаются позднее как независимые адаптеры к серверному outbox после выбора провайдера, правил подтверждения адресов, SLA и пользовательских настроек. SMS, мессенджеры и Platonus также не входят в этот этап.

Внутреннее уведомление — это запись в базе данных, а не toast. Toast и inline-ошибка дают обратную связь о текущем действии, но не заменяют постоянное уведомление. Отключить обязательные внутренние уведомления рабочего процесса нельзя.

## Почему выбран внутренний канал

- Все действия выполняются авторизованными пользователями в веб-приложении и уже имеют серверные очереди.
- В проекте нет service worker, PWA manifest, VAPID-конфигурации, mail provider и фонового delivery worker.
- Push зависит от разрешения браузера и платформы; на iOS web push требует установки приложения на домашний экран.
- Наличие строки email не означает, что адрес подтверждён и пригоден для рабочих уведомлений.
- Для первой версии не установлен SLA, требующий внешней доставки вне приложения.
- Внутренняя запись создаётся атомарно с доменным действием и не может потеряться из-за недоступности внешнего провайдера.

Существующие глобальные или localStorage-настройки email/push не управляют новым каналом. Язык, прочтение и будущие настройки внешних каналов являются пользовательскими серверными данными, а не настройками организации или устройства.

## Три разных состояния

1. **Доменное состояние** определяет, можно ли ещё выполнить действие: например, `transfer.status=pending_current_owner`.
2. **Рабочая очередь** вычисляется из актуального доменного состояния и прав: ожидающие передачи, решения сотрудника, `admin_queue`, повторные проверки техника.
3. **Уведомление** сообщает о событии и имеет собственное состояние `readAt`.

Прочтение уведомления никогда не подтверждает передачу, не закрывает решение и не удаляет элемент рабочей очереди. Устаревшая ссылка показывает актуальный статус и недоступное действие; сервер заново проверяет права, recipient, version и состояние.

## Матрица событий

| Событие | Получатель | Тип | Поведение |
| --- | --- | --- | --- |
| Свободный предмет принят | Принявший сотрудник | Нет постоянного уведомления | Успех показывается сразу, карточка обновляется |
| Запрошена передача занятого предмета | `currentResponsibleIdAtRequest` | `transfer.requested` | Actionable, ссылка на передачу |
| Передача подтверждена | `proposedResponsibleId` | `transfer.confirmed` | Outcome, ссылка на предмет/передачу |
| Передача отклонена | `requestedBy` | `transfer.rejected` | Outcome; имя текущего ответственного не раскрывается |
| Запрос отменён инициатором | `currentResponsibleIdAtRequest` | `transfer.cancelled` | Informational |
| Администратор принудительно изменил передачу | Прежний ответственный, ожидающий инициатор и новый ответственный, если он есть | `transfer.overridden` | Outcome; получатели дедуплицируются |
| Создано проблемное решение с `recipientKind=user` | Сохранённый `responsibleIdAtScan` | `decision.created` | Actionable, ссылка на неизменяемую revision решения |
| Создано решение с `recipientKind=admin_queue` | Общая очередь активных администраторов | `decision.admin_queue_created` | Actionable, случайный администратор не назначается |
| Сотрудник оспорил результат | `inspection.technicianId` | `decision.disputed` | Actionable, ссылка на повторную проверку |
| Повторная проверка снова проблемная | Тот же сохранённый `responsibleIdAtScan` пользовательского решения | `decision.recheck_requested` | Новое actionable-уведомление на новую revision |
| Повторная проверка дала `present` | Адресат закрытого решения | `decision.closed_present` | Outcome |
| Сотрудник подтвердил результат | Никто на уровне предмета | Нет постоянного уведомления | Состояние обновляется; техник получит финал всей проверки |
| Администратор разрешил пользовательское решение | Сохранённый адресат и техник проверки | `decision.resolved_by_admin` | Outcome, получатели дедуплицируются |
| Администратор разрешил решение общей очереди | Техник проверки | `decision.admin_queue_resolved` | Outcome; общая очередь обновляется у всех администраторов |
| Все решения закрыты, проверка подтверждена | `inspection.technicianId` | `inspection.confirmed` | Финальное outcome-уведомление |
| Validation, conflict, duplicate scan, camera/network error | Никто | Нет постоянного уведомления | Только inline/toast в текущем интерфейсе |

Роль `owner` не получает QR-инвентаризационные уведомления. Администратор не подписывается автоматически на все пользовательские решения: он видит их в административном реестре, а постоянное уведомление получает только для общей `admin_queue` или когда сам участвует в событии.

## Снимки получателей

- Получатели передачи сохраняются в момент создания transfer; последующая смена ответственности не перенаправляет уже созданное событие.
- Получатель решения берётся только из `responsibleIdAtScan`, а не из текущего ответственного на момент доставки.
- Для предмета без ответственного сохраняется `recipientKind=admin_queue`, `recipientId=null`.
- Новые активные администраторы видят все ещё нерешённые элементы `admin_queue`, даже если стали администраторами после создания события.
- Деактивированный пользователь не получает доступ после входа. Его незакрытое пользовательское решение появляется администратору в фильтре «Адресат недоступен» для разрешения с обязательной причиной.
- Если один пользователь попадает в несколько ролей получателей одного события, создаётся одна доставка.

## Данные

### Notification event

| Поле | Правило |
| --- | --- |
| `id` | Непрозрачный ID |
| `domainEventId` | Стабильный ID доменного события |
| `type` | Только enum из матрицы |
| `actorId` | Nullable; системное событие не подменяется пользователем |
| `subjectType` | `item`, `transfer`, `decision`, `inspection` |
| `subjectId` | Непрозрачный ID |
| `subjectRevision` | Версия/revision, к которой относится событие |
| `audienceKind` | `direct_user` или `admin_queue` |
| `safePayload` | Allowlist безопасных ID, enum и коротких display labels |
| `occurredAt` | Время доменного события в UTC |
| `createdAt` | Время фиксации записи в UTC; не используется как concurrency boundary |

В событии не хранятся готовый локализованный текст, dispute comment, административная причина, email, телефон, подписанный URL фотографии или имя скрытого текущего ответственного. Пользовательский label сохраняется и выводится как plain text, нормализуется по `docs/field-validation.md` и обрезается для preview до 120 code points.

### Direct delivery

`NotificationDelivery` содержит `eventId`, `recipientId`, положительный `mailboxSequence`, `createdAt`, nullable `readAt`. Уникальность:

```text
NotificationEvent:
(domainEventId, type, subjectType, subjectId, subjectRevision, audienceKind)

NotificationDelivery:
(eventId, recipientId)
(recipientId, mailboxSequence)
```

Уникальность event не зависит от числа direct recipients: одно доменное событие имеет одну запись, а получатели представлены deliveries. Эти ограничения вместе не позволяют повторить ни событие, ни доставку конкретному пользователю.

`NotificationMailbox` содержит одну строку на direct user и одну общую строку `admin_queue`. Перед созданием deliveries транзакция блокирует требуемые mailbox-строки в стабильном порядке, увеличивает их `nextSequence` и присваивает полученные значения новым direct deliveries. Событие общей очереди аналогично получает `adminQueueSequence` из общей строки. Изменение sequence и вставка уведомлений коммитятся или откатываются вместе с доменным действием.

Sequence принадлежит mailbox, а не глобальному времени. Транзакция чтения видит либо прежний `nextSequence` без незакоммиченного события, либо новый sequence вместе с закоммиченным событием. Поэтому начавшаяся раньше, но закоммиченная позже вставка не может получить значение меньше уже выданного клиенту cutoff.

### Admin queue receipt

Событие `audienceKind=admin_queue` не размножается по текущему списку администраторов. Пока доменное решение доступно общей очереди, оно показывается всем активным администраторам как actionable и считается непрочитанным для администратора без receipt. Индивидуальная таблица `NotificationReceipt(eventId, userId, readAt)` хранит прочтение. Уникальность `(eventId, userId)`.

Прочтённое администратором событие остаётся непрочитанным у других администраторов. Разрешение доменного решения убирает actionable-элемент у всех, но не переписывает их историю прочтения.

После разрешения событие общей очереди до конца retention остаётся read-only в истории любого пользователя, который сейчас является активным администратором, включая администратора, активированного позднее. Оно помечается закрытым по актуальному доменному состоянию, не требует receipt для просмотра и никогда не входит в unread badge или actionable-фильтр. Деактивированный администратор сразу теряет доступ; повторная активация восстанавливает только обычный ролевой доступ к истории, но не создаёт непрочитанное событие задним числом.

## Атомарность и дедупликация

- Доменное изменение, audit record, `NotificationEvent` и direct deliveries создаются в одной PostgreSQL-транзакции.
- Если обязательная внутренняя запись не создалась, доменная команда откатывается целиком.
- Повтор команды с тем же idempotency record возвращает прежний ответ и не создаёт уведомления повторно.
- DB unique constraints являются последней защитой от дублей.
- Для события с несколькими получателями набор пользователей сначала дедуплицируется.
- Порядок ленты: `occurredAt DESC, id DESC`; pagination cursor содержит оба значения. Этот display cursor не используется для массового прочтения.
- Транзакция изменяет доменную сущность до построения safe payload, поэтому уведомление всегда ссылается на закоммиченную revision.

## Прочтение

- Открытие списка само по себе ничего не отмечает.
- Открытие конкретного уведомления может вызвать явную idempotent-команду mark-read.
- Команда `{ notificationId }` доступна только direct recipient; для admin queue создаёт/обновляет receipt текущего администратора.
- Повторное прочтение возвращает успех без новой audit-записи.
- Ответ списка содержит `directThroughSequence` из direct mailbox пользователя и, только для активного администратора, `adminQueueThroughSequence` из общей mailbox. «Отметить все прочитанными» передаёт эти два непрозрачных положительных cutoff.
- Сервер помечает direct deliveries только с `mailboxSequence <= directThroughSequence`. Для всё ещё нерешённых admin-queue событий с `adminQueueSequence <= adminQueueThroughSequence` он создаёт receipts текущего администратора. Закрытые события receipt не требуют.
- Событие, которого не было в согласованном snapshot списка, получает sequence выше соответствующего cutoff и остаётся непрочитанным, даже если его `occurredAt` старше. Повтор mark-all с теми же cutoff идемпотентен.
- Счётчик включает непрочитанные direct deliveries и только нерешённые admin-queue события без read receipt текущего администратора. Закрытые события общей очереди в счётчик не входят независимо от receipt.
- Read/unread не является security-событием и не требует доменного аудита; административное разрешение и другие действия аудируются отдельно.

## Получение обновлений

Первая версия не обещает real-time:

- обновление после входа, навигации, возврата вкладки в focus и успешной доменной команды;
- polling раз в 60 секунд, только пока вкладка видима и пользователь online;
- exponential backoff при сетевой ошибке, сброс после успешного ответа;
- один запрос на вкладку в момент времени;
- серверная пагинация и отдельный лёгкий endpoint счётчика.

WebSocket, SSE, фоновые browser sync и звуки не входят в MVP. Отсутствие polling не влияет на сохранность: запись уже находится в базе.

## Доступ и приватность

- Лента и deep link требуют действующую сессию и повторную server-side авторизацию к subject.
- ID уведомления не даёт доступа к предмету, передаче, проверке, comment или фото.
- Скрытый текущий ответственный не попадает в payload передачи и не раскрывается requester через текст, URL или error.
- Preview не содержит комментарий спора, административную причину, фото и персональные контакты.
- Для результата используется сохранённый recipient; текущий ответственный не получает доступ автоматически.
- Signed photo URLs никогда не сохраняются в уведомлении.
- Удалённое/недоступное основание показывает нейтральное «Действие больше недоступно», не раскрывая причину отсутствия.

## Локализация

Сервер возвращает `type`, safe payload и UTC timestamp. Клиент рендерит текст по текущему пользовательскому locale `ru`, `kk` или `en`; отсутствие перевода падает в `ru`, затем в безопасный generic key. CI проверяет одинаковый набор ключей во всех трёх словарях.

| Key | Русский | Қазақша | English |
| --- | --- | --- | --- |
| `transfer.requested` | Ожидается ваше решение по передаче предмета. | Затты беру бойынша сіздің шешіміңіз күтілуде. | Your decision on an item transfer is required. |
| `transfer.confirmed` | Передача предмета подтверждена. | Затты беру расталды. | The item transfer was confirmed. |
| `transfer.rejected` | Запрос на передачу отклонён. | Затты беру сұрауы қабылданбады. | The item transfer request was rejected. |
| `transfer.cancelled` | Запрос на передачу отменён инициатором. | Затты беру сұрауын бастамашы болдырмады. | The item transfer request was cancelled by its requester. |
| `transfer.overridden` | Передача предмета изменена администратором. | Затты беруді әкімші өзгертті. | The item transfer was changed by an administrator. |
| `decision.created` | Подтвердите или оспорьте результат проверки предмета. | Затты тексеру нәтижесін растаңыз немесе даулаңыз. | Confirm or dispute the item inspection result. |
| `decision.admin_queue_created` | Новое решение ожидает администратора. | Жаңа шешім әкімшіні күтуде. | A new decision requires an administrator. |
| `decision.disputed` | Результат оспорен. Требуется повторная проверка. | Нәтиже дауланды. Қайта тексеру қажет. | The result was disputed. A recheck is required. |
| `decision.recheck_requested` | Повторная проверка завершена. Требуется ваше решение. | Қайта тексеру аяқталды. Сіздің шешіміңіз қажет. | The recheck is complete. Your decision is required. |
| `decision.closed_present` | Повторная проверка закрыла проблему. | Қайта тексеру мәселені жапты. | The recheck resolved the issue. |
| `decision.resolved_by_admin` | Решение по результату закрыто администратором. | Нәтиже бойынша шешімді әкімші жапты. | The result decision was closed by an administrator. |
| `decision.admin_queue_resolved` | Решение общей очереди закрыто. | Жалпы кезектегі шешім жабылды. | The shared-queue decision was closed. |
| `inspection.confirmed` | Проверка подтверждена. | Тексеру расталды. | The inspection was confirmed. |
| `notification.unavailable` | Действие больше недоступно. | Әрекет енді қолжетімсіз. | The action is no longer available. |

Дата показывается в пользовательской timezone; при отсутствии настройки используется `Asia/Aqtau`. Пользовательские labels экранируются и не вставляются в грамматически чувствительные части шаблона.

## Доступность

- Центр является семантическим списком; у элемента есть заголовок, время, статус и понятная ссылка.
- Все действия доступны с клавиатуры, имеют видимый focus и не кодируются только цветом.
- Счётчик имеет accessible label с локализованным числом непрочитанных.
- Новое уведомление объявляется через polite live region и не перехватывает focus.
- Автоматический звук, вибрация и всплывающее browser-разрешение не используются.
- При группировке по проверке каждый исходный actionable-элемент остаётся доступен отдельно.

## Хранение

- Actionable-уведомление хранится минимум до закрытия доменного действия; после закрытия оно становится read-only history.
- После закрытия direct delivery/event/receipt хранится 365 дней; audit и доменная история имеют собственную retention policy.
- Purge не удаляет незакрытое действие и не влияет на аудит.
- При деактивации пользователя записи не переназначаются и не раскрываются другим сотрудникам.
- Удаление пользователем отдельных обязательных уведомлений в MVP отсутствует; доступна только отметка прочтения.

## Граница будущих адаптеров

`ExternalNotificationOutbox` создаётся как техническая граница, но в MVP ни один внешний worker не включён и строки внешней доставки не создаются, потому что нет включённых внешних каналов. Будущий adapter будет создавать outbox-запись в исходной доменной транзакции только для включённого канала и получает generic privacy-safe payload. Delivery работает at-least-once:

- unique event/channel/recipient key;
- exponential backoff с jitter;
- классификация временных и permanent failures;
- attempt log и provider message ID;
- подтверждённый email либо действующая push subscription;
- generic preview без комментариев, фотографий, причин и персональных данных;
- пользовательские preferences, quiet hours и правила обязательности, согласованные отдельно.

Наличие outbox не является обещанием email или push. Флаги без реально настроенного провайдера не показываются пользователю.

## Не входит в первую версию

- Web push, PWA manifest, service worker, VAPID и управление browser subscriptions.
- Email provider, шаблоны писем, bounce/complaint handling, unsubscribe и проверка адресов.
- SMS, мессенджеры, Platonus, native mobile notifications.
- Digests, напоминания, escalation timers, SLA и quiet hours.
- WebSocket/SSE и cross-device real-time read synchronization.
- Возможность отключать обязательные внутренние workflow-уведомления.

## Приёмочные критерии

- Каждый event из матрицы создаёт ровно требуемый набор внутренних уведомлений либо явно не создаёт их.
- Получатель передачи и решения берётся из snapshot, а не из текущего состояния при чтении.
- `admin_queue` видна всем активным администраторам и не назначается случайному пользователю.
- Доменное действие, аудит и уведомление атомарны; retry не создаёт дубль.
- Read не меняет доменное состояние; resolve не зависит от read.
- Лента, счётчик, mark-read и mark-all-read корректны при конкурентных новых событиях.
- Deep link и preview не раскрывают скрытого ответственного, comments, причины и фото.
- Устаревшее или уже закрытое действие безопасно показывает актуальный статус.
- Деактивированный адресат не оставляет проблему невидимой для администратора.
- Тексты имеют одинаковые ключи в `ru`, `kk`, `en` и доступны с клавиатуры/screen reader.
- Без настроенных внешних adapters система полноценно работает на внутреннем канале.

## Минимальная тестовая матрица реализации

| Область | Обязательные случаи |
| --- | --- |
| Матрица событий | Каждый event, явное отсутствие free-accept/validation уведомлений, dedupe одного пользователя |
| Снимки | Передача ответственности после event, `responsibleIdAtScan`, новый предмет, новый/деактивированный admin |
| Транзакция | Rollback domain/audit/notification, idempotent retry, DB unique race |
| Прочтение | Direct owner only, admin receipt, repeat read, dual mailbox cutoff, начавшийся раньше/поздно закоммиченный event, concurrent newer event |
| Очередь | Read не resolve, stale link, superseded revision, concurrent admins, already resolved |
| Приватность | Скрытый owner, comment/reason/photo URL отсутствуют, deep-link reauthorization, non-enumeration |
| Лента | Cursor ordering при одинаковом времени, pagination, retention, deleted subject |
| Polling | Hidden/offline, one in-flight, backoff/reset, refresh after mutation |
| i18n/a11y | Key parity, fallback, timezone, escaping/truncation, keyboard/focus/live region |
| External boundary | Worker выключен, outbox не влияет на MVP, нет ложных email/push toggles |
