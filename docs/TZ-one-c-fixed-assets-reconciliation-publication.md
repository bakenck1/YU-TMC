# Техническое задание: сверка и публикация основных средств из 1С

Версия: 1.1
Дата: 22 сентября 2026 года
Статус: готово к реализации
Текущий снимок: выгрузка 1С от 22 сентября 2026 года, 10 617 записей

## 1. Решение

Текущие данные 1С уже приняты сервером и находятся в промежуточной таблице
`yu_inventory.one_c_fixed_asset_inbox`. Повторно загружать их в этот же endpoint не требуется.

Следующий этап должен реализовать управляемую сверку и публикацию данных из промежуточного
реестра в основной каталог `yu_inventory.items`.

До завершения этого этапа:

- новые выгрузки 1С не публикуются автоматически;
- существующие 372 предмета не изменяются автоматически;
- текущие корпуса, этажи, кабинеты, фотографии, ответственные и история операций сохраняются;
- записи 1С остаются доступными для проверки администраторами;
- удаление данных из inbox вручную запрещено.

## 2. Фактическое состояние

### 2.1. Работает сейчас

- `POST /api/integrations/1c/fixed-assets` принимает XML по Bearer-ключу.
- Лимит одного запроса — 50 000 записей и 64 MiB.
- Импорт атомарен и идемпотентен по постоянному GUID 1С.
- Повторный GUID обновляет JSON payload только при изменении данных.
- Полностью совпадающий payload учитывается как `unchanged`.
- Вся партия откатывается при ошибке в одной записи или ошибке базы данных.
- Данные сохраняются только в `one_c_fixed_asset_inbox`.

### 2.2. Результат текущей выгрузки

Последний подтверждённый запрос от 22 сентября 2026 года:

```text
received: 10617
created: 4065
updated: 11
unchanged: 6541
requestId: a03f1599-dcd4-435a-9bba-36a6c5e22c9b
```

Сумма результатов равна 10 617. При этом `updated + unchanged = 6 552`, то есть новая полная
выгрузка охватила все ранее сохранённые записи и добавила ещё 4 065 GUID. Прежнее расхождение
между 6 548 и 6 552 больше не означает наличие строк вне последнего среза.

Для точной фиксации снимка требуется исходный файл `inventory_20260922_131141.xml` и его SHA-256.
Текущая inbox-таблица по-прежнему не хранит состав и hash каждого запроса отдельно.

Проверка production inbox от 22 сентября 2026 года:

| Статус 1С | Количество |
|---|---:|
| `Принято к учёту` | 6 548 |
| `Снято с учёта` | 648 |
| `Не в учёте` | 3 421 |
| **Всего** | **10 617** |

Пустых или неизвестных статусов нет. Резервная копия после приёма снимка завершилась с
`Result=success` и `ExecMainStatus=0`.

По аудиту предыдущего снимка от 19 сентября были выявлены проблемы качества:

- 4 записи без инвентарного номера;
- 2 записи без подразделения/локации;
- 6 записей без ответственного;
- 8 ОС с исходной отрицательной остаточной стоимостью сохранены со значением `0`;
- в данных присутствуют недвижимость, программное обеспечение, документация и служебная
  запись «Корректировка»;
- подразделение 1С не является физическим корпусом, этажом или кабинетом Inventory.

После выгрузки 10 617 строк эти счётчики необходимо пересчитать: 11 существующих записей были
обновлены, а 4 065 записей добавлены. Старые значения нельзя считать итоговой проверкой нового
снимка.

### 2.3. Не работает сейчас

- нет связи GUID 1С с `items.id`;
- нет сравнения inbox с существующими 372 предметами;
- нет истории и состава отдельных импортов;
- нет интерфейса проверки и разрешения конфликтов;
- нет безопасной публикации в основной каталог;
- нет автоматического отображения 10 617 строк на странице `/items`;
- отсутствие GUID в следующей выгрузке не снимает ОС с учёта и не удаляет его.

## 3. Цели

1. Зафиксировать текущую выгрузку как неизменяемый импортный снимок.
2. Сопоставить ОС 1С с существующими предметами без дублей.
3. Отделить бухгалтерские сведения от физических данных Inventory.
4. Дать администратору предварительный просмотр каждого изменения.
5. Публиковать только проверенные физические ТМЦ.
6. Сохранить полную историю решений, публикаций и ошибок.
7. Обеспечить повторный запуск без повторного создания предметов.
8. Подготовить архитектуру для будущих выгрузок, но не включать их автоматическую публикацию.

## 4. Что не входит в первую версию

- автоматическое удаление предметов, отсутствующих в XML;
- автоматическое списание без решения администратора;
- автоматическое определение кабинета по подразделению;
- автоматическая привязка ответственного только по совпадению ФИО;
- публикация недвижимости, ПО, документации и служебных бухгалтерских записей;
- двусторонняя отправка изменений из Inventory обратно в 1С;
- автоматическая публикация новых ежедневных выгрузок;
- изменение действующих процессов передачи, инвентаризации, QR, фотографий и заявок.

## 5. Обязательные бизнес-правила

### 5.1. Область публикации

По умолчанию публикуются только физические движимые ОС, которые могут быть представлены как
предмет Inventory.

До отдельного письменного решения исключаются:

- недвижимость и помещения;
- программное обеспечение и лицензии;
- проектная и техническая документация;
- бухгалтерские корректировки;
- строки без инвентарного номера;
- строки без выбранного физического кабинета;
- строки с неразрешённым конфликтом инвентарного номера;
- строки, для которых невозможно определить допустимый тип ТМЦ.

Исключение означает статус проверки, а не удаление исходной строки.

### 5.2. Владение полями

| Поле | Источник истины | Правило |
|---|---|---|
| GUID 1С | 1С | Неизменяемый внешний идентификатор |
| Код 1С | 1С | Справочное поле, не заменяет GUID |
| Инвентарный номер | 1С после подтверждения | Уникален в Inventory; конфликт блокирует публикацию |
| Название | 1С с предварительным сравнением | Обновление существующего предмета только после подтверждения |
| Остаточная стоимость | 1С/бухгалтерия | Хранить отдельно от `unit_price`; ноль и отсутствие различать |
| Статус бухгалтерского учёта | 1С | Не менять статус Inventory автоматически |
| Подразделение | 1С | Хранить как бухгалтерское подразделение, не как кабинет |
| Корпус, этаж, кабинет | Inventory | Никогда не заменять строкой `Location` из 1С |
| Ответственный Inventory | Inventory | Привязка только по устойчивому ID или ручному решению |
| ФИО ответственного 1С | 1С | Справочное значение для сверки |
| Фото, состояние, подключение | Inventory | Не изменять импортом 1С |
| История передач и заявок | Inventory | Не изменять импортом 1С |

### 5.3. Стоимость

`ResidualValue` из 1С является остаточной бухгалтерской стоимостью. Она не должна автоматически
записываться в существующее поле `items.unit_price`, потому что это разные экономические понятия.

Необходимо отдельное nullable-поле/проекция `accounting_residual_value`.

- отсутствие стоимости хранится как `NULL`;
- подтверждённый ноль хранится как `0`;
- отрицательное значение создаёт блокирующую проблему проверки;
- восемь известных строк со значением `0` маркируются как требующие подтверждения бухгалтерии;
- исправление от 1С с тем же GUID должно обновлять остаточную стоимость без создания дубля.

### 5.4. Локация

`Location` из 1С сейчас содержит подразделение (`АУП`, `ППС`, `Транспортный отдел` и т. п.).
Оно сохраняется отдельно как `source_department`.

Для нового предмета администратор обязан выбрать существующий `room_id`. Фиктивный кабинет
«Неизвестно» автоматически не создаётся.

При связывании с существующим предметом его `room_id` сохраняется. Изменение кабинета возможно
только через существующий процесс Inventory и должно попасть в аудит.

### 5.5. Ответственный

- `ResponsibleGUID` является предпочтительным ключом, если 1С начнёт его передавать.
- При отсутствии GUID совпадение ФИО используется только как подсказка.
- Автоматическая привязка по одному ФИО запрещена.
- Пустой ответственный допускает публикацию только как «не закреплено», если это подтверждено
  администратором.
- Импорт не должен закрывать действующий период ответственности у существующего предмета без
  отдельного подтверждения.

### 5.6. Статусы

| Статус 1С | Предлагаемое действие |
|---|---|
| `Принято к учёту` | Предложить активный предмет; существующий статус не менять автоматически |
| `Снято с учёта` | Создать задачу на проверку списания; автоматическое списание запрещено |
| `Не в учёте` | Оставить в проверке и не публиковать без решения администратора |

Отсутствие записи в новом срезе не считается удалением или списанием.

### 5.7. Списанные ОС из 1С

Строки со статусом `Снято с учёта` должны отображаться в отдельном read-only подразделе страницы
`/items/decommissioned` с заголовком «Списанные по данным 1С». До сверки они не создаются в
`yu_inventory.items` и не смешиваются с предметами, списанными штатным процессом Inventory.

Для каждой строки показывать:

- GUID, код и инвентарный номер 1С;
- название;
- бухгалтерское подразделение и ответственное лицо из 1С;
- остаточную стоимость;
- статус учёта 1С;
- время последнего получения из 1С;
- состояние связи с предметом Inventory;
- обнаруженные конфликты.

Правила:

- статус `Снято с учёта` не меняет `items.status` автоматически;
- если строка связана с действующим предметом, создаётся задача на подтверждение списания;
- перевод связанного предмета в `decommissioned` выполняется только штатным сервисом Inventory с
  автором, причиной, датой и записью аудита;
- несвязанная строка остаётся справочной и не получает QR, кабинет, фото, передачи или действия
  редактирования;
- статус `Не в учёте` показывается отдельным фильтром проверки и не приравнивается к списанию;
- `updated_at` inbox подписывается как «Получено из 1С», а не как «Дата списания»;
- дата списания отображается только после добавления отдельного исходного поля в контракт 1С.

## 7. Фиксация текущего снимка

Перед разработкой публикации необходимо:

1. Получить `inventory_20260922_131141.xml`.
2. Проверить SHA-256 и сохранить его в batch.
3. Повторно прогнать файл через действующий parser без записи в `items`.
4. Убедиться, что XML содержит 10 617 уникальных GUID.
5. Сравнить множество GUID файла с 10 617 строками inbox.
6. Убедиться, что отсутствующих и дополнительных GUID нет; любое расхождение блокирует публикацию.
7. Создать immutable batch из 10 617 строк.
8. Зафиксировать восемь проблем стоимости отдельными issues.
9. Рассчитать точное распределение по трём статусам 1С до принятия решений о публикации.
10. Сохранить резервную копию до любых публикаций.

Пункты 9 и 10 выполнены 22 сентября 2026 года: распределение равно 6 548 / 648 / 3 421,
резервная копия завершена успешно.

Если исходный XML получить невозможно, допускается создать batch из текущего inbox, но он должен
быть помечен `unverified_legacy_snapshot`, а автоматическая массовая публикация запрещается.

## 8. Сопоставление с существующими 372 предметами

### 8.1. Порядок поиска кандидата

1. Существующая запись `item_one_c_links` по GUID — точное совпадение.
2. Точное совпадение нормализованного официального инвентарного номера — кандидат на связь.
3. Точное совпадение официального штрихкода — кандидат на связь.
4. Код 1С, название, подразделение и ФИО могут использоваться только как подсказки.
5. Нечёткое совпадение названия никогда не создаёт автоматическую связь.

Для нормализации инвентарного номера использовать действующий механизм
`inventory_number_key`; отдельный несовместимый алгоритм не создавать.

### 8.2. Результаты анализа

Каждая строка получает ровно один результат:

- `linked_exact_guid` — уже связана;
- `candidate_inventory_number` — найден один предмет по номеру;
- `conflict_inventory_number` — номер занят несовместимым предметом;
- `new_publishable` — кандидат на создание;
- `blocked_missing_inventory_number`;
- `blocked_missing_room`;
- `blocked_unsupported_type`;
- `excluded_non_physical`;
- `manual_review`.

### 8.3. Защита существующих предметов

При связывании запрещено автоматически менять:

- `room_id`;
- текущего ответственного;
- фотографию;
- состояние и подключение;
- статус обслуживания/списания;
- историю передач;
- QR и локальные штрихкоды;
- комментарии, заявки и результаты инвентаризаций.

Администратор видит diff названия и инвентарного номера и отдельно подтверждает изменения.

### 8.4. Сверка инвентарного номера и штрихкода

Основным идентификатором объекта 1С остаётся GUID. Инвентарный номер и штрихкод используются
для поиска существующего предмета и проверки правильности связи.

В Inventory официальный штрихкод предмета уже связан с его инвентарным номером через
`barcode_registry`. Новый отдельный реестр штрихкодов для 1С создавать запрещено.

Правила нормализации:

- для сравнения инвентарных номеров использовать существующую
  `inventoryNumberComparisonKey`: Unicode NFKC, удаление пробелов по краям и приведение регистра;
- не удалять автоматически внутренние пробелы, `/`, `-` и другие значимые символы;
- дополнительное «мягкое» сравнение без разделителей разрешено только как подсказка;
- мягкое совпадение никогда не создаёт связь автоматически;
- для считанного Code 39 использовать существующую `parseCode39ScanInput`;
- обрамляющие `*` Code 39 и поддерживаемый legacy-префикс обрабатываются действующим parser;
- исходные значения всегда сохраняются и показываются администратору без потери форматирования.

Поле `Barcode` в текущей выгрузке 1С может отсутствовать. Это не ошибка и не конфликт.
В таком случае система показывает «Штрихкод 1С не передан» и выполняет сверку по GUID и
`InventoryNumber`. Нельзя записывать выдуманный barcode в источник 1С.

Для визуального Code 39 Inventory может использовать подтверждённый официальный инвентарный
номер через действующую `code39PayloadForInventoryNumber`. Это штрихкод Inventory, а не значение,
которое якобы пришло из 1С.

### 8.5. Матрица результатов сравнения

| GUID-связь | Инвентарный номер | Штрихкод 1С | Результат | Действие |
|---|---|---|---|---|
| Есть | Совпадает | Пустой или указывает на тот же item | `match_ok` | Показать «Совпадает», разрешить no-change/update после проверки diff |
| Нет | Точно совпадает с одним item | Совпадает с тем же item | `strong_candidate` | Предложить связь; первое связывание подтверждает администратор |
| Нет | Точно совпадает с одним item | Пустой | `inventory_candidate` | Показать «Номер совпал, штрихкод 1С не передан»; требуется подтверждение |
| Есть/нет | Совпадает с item A | Указывает на item B | `barcode_conflict` | Красный конфликт, публикация заблокирована |
| Есть/нет | Не совпадает | Указывает на существующий item | `inventory_number_conflict` | Показать оба номера и связанный item, публикация заблокирована |
| Есть | Изменился | Пустой | `linked_number_changed` | Показать старый и новый номер; требуется отдельное подтверждение |
| Нет | Только мягкое совпадение | Пустой/неизвестный | `possible_match` | Только подсказка, ручной выбор |
| Нет | Совпадений нет | Совпадений нет или пустой | `new_candidate` | Проверить остальные обязательные поля и предложить создание |
| Любая | Номер занят несколькими/несовместимыми объектами | Любой | `ambiguous_conflict` | Ручное исправление данных, автоматическое действие запрещено |

Условия статуса «Всё совпадает»:

1. GUID уже связан с тем же `item_id` либо администратор подтверждает первое точное совпадение;
2. нормализованный `InventoryNumber` 1С равен `items.inventory_number_key`;
3. если `Barcode` 1С передан, он разрешается через общий barcode registry в тот же `item_id`;
4. ни номер, ни barcode не принадлежат другому предмету;
5. отсутствуют другие блокирующие проблемы строки.

Если хотя бы один переданный идентификатор указывает на другой предмет, интерфейс обязан показать
конфликт, а сервер обязан отклонить публикацию независимо от состояния кнопки на клиенте.

### 8.6. Отображение сверки идентификаторов

В таблице и карточке сравнения добавить:

- инвентарный номер 1С;
- код 1С;
- штрихкод 1С или «Не передан»;
- текущий инвентарный номер Inventory;
- официальный barcode registry Inventory;
- локальные штрихкоды только для справки;
- статус сравнения;
- понятное описание несовпадения;
- ссылку на найденный предмет.

Цветовые состояния:

- зелёный — `match_ok`;
- синий — кандидат, требующий первого подтверждения;
- жёлтый — неполные данные или мягкое совпадение;
- красный — конфликт, публикация заблокирована;
- серый — новая или исключённая запись.

Фильтры:

- всё совпадает;
- номер совпал, barcode не передан;
- не совпадает инвентарный номер;
- не совпадает barcode;
- возможный дубль;
- новый предмет;
- отсутствует инвентарный номер.

### 8.7. Серверная проверка перед связыванием

Перед записью `item_one_c_links` сервер повторно, внутри транзакции:

1. блокирует выбранный item на время проверки;
2. повторно читает `items.inventory_number_key`;
3. повторно читает все записи `barcode_registry` для кандидата;
4. проверяет, что номер/barcode не были заняты после dry-run;
5. проверяет optimistic version предмета;
6. создаёт связь и audit record атомарно.

Для нового предмета официальный barcode registry создаётся только существующим доменным процессом
создания item. Прямой INSERT в `barcode_registry` из интеграции запрещён.

## 9. Создание новых предметов

Новый `items` создаётся только если:

- строка относится к физическому движимому ОС;
- присутствует уникальный инвентарный номер;
- выбрана существующая комната;
- выбран допустимый `item_type`;
- отсутствуют конфликты barcode/инвентарного номера;
- администратор явно подтвердил публикацию;
- значение количества является допустимым;
- решение и исходный batch записаны в аудит.

Значения по умолчанию:

- `inventory_number_kind = official`;
- `status = active` только для «Принято к учёту»;
- `condition = good` только как явно подтверждённый default;
- `connection_status = not_applicable`;
- `created_by` и `updated_by` — администратор публикации;
- фотографии не создаются;
- фиктивные QR и штрихкоды не создаются.

Если `quantity > 1`, строка блокируется для ручного решения: ОС с индивидуальным инвентарным
номером обычно должно иметь количество 1.

## 10. Интерфейс администратора

Создать раздел `/settings/integrations/1c` только для администраторов.

### 10.1. Список выгрузок

Показывать:

- дату и время;
- имя и SHA-256 файла;
- requestId;
- количество строк;
- статус анализа и публикации;
- количество совпадений, новых, конфликтных, заблокированных и исключённых;
- автора подтверждения;
- ссылку на журнал публикации.

### 10.2. Карточки итогов

- всего строк;
- связано с существующими;
- готово к созданию;
- конфликты;
- отсутствует инвентарный номер;
- не назначен кабинет;
- не определён тип;
- финансовые проблемы;
- нефизические ОС;
- опубликовано.

### 10.3. Таблица сверки

Колонки:

- статус проверки;
- GUID и код 1С;
- инвентарный номер;
- название;
- тип/категория;
- подразделение 1С;
- выбранные корпус, этаж и кабинет;
- ответственный 1С;
- связанный пользователь Inventory;
- остаточная стоимость;
- найденный предмет;
- предлагаемое действие;
- проблемы;
- решение администратора.

Фильтры и поиск выполняются на сервере с пагинацией. Загружать все 10 617 строк в браузер одним
ответом запрещено.

### 10.4. Экран сравнения

Для кандидата на связь показывать две колонки:

```text
Данные 1С | Текущие данные Inventory
```

Изменённые поля выделяются. Администратор может:

- связать без изменения предмета;
- принять выбранные изменения;
- оставить значение Inventory;
- выбрать другой предмет;
- исключить строку;
- вернуть строку на ручную проверку.

### 10.5. Массовые действия

Разрешены только для строк без конфликтов:

- подтвердить точные совпадения по инвентарному номеру;
- назначить тип для выбранных строк;
- назначить кабинет выбранным строкам;
- исключить выбранные нефизические ОС;
- подтвердить создание выбранных строк.

Перед действием показывать количество затрагиваемых строк и итоговый diff. Все массовые действия
записывать в аудит.

### 10.6. Списанные по данным 1С

На `/items/decommissioned` добавить две явно разделённые вкладки:

1. «Списанные в Inventory» — существующий список из `items` со статусами `decommissioned` и
   `decommissioned_in_use`.
2. «Списанные по данным 1С» — read-only список строк текущего batch со статусом
   `Снято с учёта`.

Над второй вкладкой показывать предупреждение: «Данные получены из 1С и ещё не опубликованы в
Inventory». Счётчики вкладок вычислять независимо. У строки, связанной с активным предметом,
показывать действие «Проверить списание»; массовое автоматическое списание запретить.

## 11. Внутренний API

Добавить администраторские endpoints:

```text
GET  /api/integrations/1c/batches
GET  /api/integrations/1c/batches/:id
GET  /api/integrations/1c/batches/:id/rows
GET  /api/integrations/1c/decommissioned
POST /api/integrations/1c/batches/:id/analyze
PATCH /api/integrations/1c/batches/:id/rows/:externalId/decision
POST /api/integrations/1c/batches/:id/decisions/bulk
POST /api/integrations/1c/batches/:id/approve
POST /api/integrations/1c/batches/:id/publish
GET  /api/integrations/1c/publications/:id
```

Текущий внешний POST остаётся Bearer API и не получает пользовательскую сессию.

Администраторские endpoints требуют новую permission:

```text
inventory.integration.one_c.manage
```

Permission выдаётся только роли `admin`. Проверка выполняется на сервере для каждого запроса.

`GET /api/integrations/1c/decommissioned` возвращает только серверную пагинацию, фильтры и
read-only DTO. Endpoint не должен возвращать Bearer-ключ, исходный XML или произвольный JSONB
payload целиком.

## 12. Анализ и dry-run

Перед публикацией система формирует детерминированный план:

```json
{
  "batchId": "...",
  "sourceHash": "...",
  "existingItemsVersion": "...",
  "create": 0,
  "link": 0,
  "update": 0,
  "exclude": 0,
  "blocked": 0,
  "conflicts": 0
}
```

Dry-run:

- не изменяет `items`;
- проверяет уникальность номеров и barcode;
- проверяет существование комнат и пользователей;
- проверяет версии связанных предметов;
- показывает точный итог;
- сохраняет hash плана.

Если данные или решения изменились после dry-run, публикация отклоняется и требует повторного
анализа.

## 13. Публикация

1. Публиковать только batch в состоянии `approved`.
2. Использовать idempotency key на всю публикацию.
3. Обрабатывать строки контролируемыми порциями до 100 записей.
4. Создание/изменение предмета, создание связи и audit record выполнять в одной транзакции.
5. При конфликте версии конкретная строка переходит в `failed/manual_review`; остальные уже
   подтверждённые строки не дублируются при повторе.
6. Повторный запуск продолжает незавершённую публикацию.
7. Один batch не может публиковаться двумя процессами одновременно.
8. После завершения сумма результатов должна равняться числу утверждённых строк.

Первый production-запуск выполнять пилотом 10–20 предметов. После ручной проверки карточек,
поиска, QR и локаций разрешить следующую порцию.

## 14. Обновление уже связанных предметов

Новая выгрузка никогда не обновляет `items` непосредственно.

Она создаёт новый batch и diff:

- изменения бухгалтерских полей можно подтвердить массово;
- изменение названия требует просмотра;
- изменение инвентарного номера требует проверки общего barcode namespace;
- изменение подразделения не меняет кабинет;
- изменение ФИО не меняет ответственного автоматически;
- «Снято с учёта» создаёт отдельное решение администратора;
- отсутствие в срезе создаёт предупреждение, но не удаление.

## 15. Аудит, журнал и наблюдаемость

Записывать:

- requestId и batchId;
- SHA-256 XML;
- количество строк и счётчики;
- пользователя каждого решения;
- старое и новое значение изменённых полей;
- причины исключения;
- начало, завершение и длительность анализа/публикации;
- idempotency key;
- ошибки по безопасному коду без секретов и персональных данных в свободном тексте.

Метрики:

- принятые batch;
- время анализа;
- количество конфликтов;
- количество опубликованных/ошибочных строк;
- задержка inbox → publication;
- повторные запросы и 429;
- ошибки БД и timeout.

API-ключ и `DATABASE_URL` никогда не выводятся в UI, логи или audit payload.

## 16. Резервное копирование и откат

Перед каждым этапом массовой публикации обязателен успешный backup.

Откат публикации не должен выполняться простым восстановлением всей production-базы, если после
публикации пользователи уже внесли другие изменения.

Для каждой созданной/изменённой строки сохранять:

- item id;
- полное before-состояние;
- after-состояние;
- версию;
- созданную внешнюю связь;
- связанные audit ids.

Автоматический компенсирующий откат допускается только до появления последующих операций над
предметом. Иначе создаётся ручная задача администратора.

## 17. Безопасность

- внешний POST сохраняет действующую Bearer-аутентификацию;
- администраторский интерфейс использует session authentication и server-side permission;
- BOLA-проверки применяются к batch, row, item и publication id;
- решения принимаются только для batch, доступного текущему администратору;
- размеры body и коллекций остаются ограниченными;
- XML entities, DTD, namespaces и wrapper-элементы остаются запрещёнными;
- payload не вставляется в HTML без экранирования;
- PII ответственных не включается в публичные ответы;
- экспорт исходного XML доступен только администратору и журналируется;
- конкурентная публикация блокируется advisory lock/lease.

## 18. Производительность

- 10 617 строк должны анализироваться без загрузки всей коллекции в память браузера;
- серверная пагинация — не более 100 строк на страницу по умолчанию;
- публикация — порциями до 100 строк;
- индексы требуются по batch/state/action/external id/matched item;
- поиск использует нормализованные ключи и индексируемые поля, а не полный scan JSONB;
- основной список после публикации остаётся ниже текущего предела 25 000 записей;
- тяжёлые анализы и публикации выполняются как отслеживаемые операции, а не в одном UI-request.

## 19. Тестирование

### 19.1. Модульные тесты

- классификация физического/нефизического ОС;
- нормализация инвентарного номера;
- mapping статусов;
- различие `NULL`, `0` и положительной стоимости;
- правила владения полями;
- match decision tree;
- формирование issues;
- hash и идемпотентность плана.
- точное сравнение инвентарного номера существующим comparison key;
- отличие точного совпадения от мягкого совпадения без разделителей;
- пустой Barcode 1С не считается конфликтом;
- barcode и номер, указывающие на разные items, создают блокирующий конфликт;
- обработка Code 39 с `*`, legacy-префиксом и недопустимыми символами.

### 19.2. PostgreSQL integration

- immutable batch и уникальность SHA-256;
- состав batch из 10 617 GUID;
- связь один GUID ↔ один item;
- конфликт инвентарного номера;
- атомарность строки публикации;
- безопасный повтор публикации;
- advisory lock;
- rollback на ошибке;
- optimistic version conflict;
- runtime role не получает лишних DDL/DELETE прав.

### 19.3. Route/security

- только admin получает доступ;
- warehouse/employee получают 403;
- BOLA на batch/row/publication;
- invalid body и collection limits;
- idempotency key;
- безопасные ошибки без SQL/секретов.

### 19.4. Компонентные и браузерные тесты

- список batch;
- фильтры и пагинация;
- diff двух источников;
- ручное и массовое решение;
- dry-run;
- подтверждение публикации;
- отображение прогресса и ошибок;
- адаптивность;
- проверка опубликованного предмета в `/items` и карточке;
- сохранность фото, кабинета и ответственности существующего предмета.
- отдельные вкладки списанных Inventory и списанных по данным 1С;
- отсутствие мутаций `items` при открытии, фильтрации и пагинации списка 1С;
- `Снято с учёта` создаёт задачу проверки, но не меняет статус предмета без подтверждения;
- `Не в учёте` не попадает в список списанных.

### 19.5. Production smoke

- публикация 10–20 пилотных строк;
- повторный запуск не создаёт дубли;
- поиск по инвентарному номеру находит предмет;
- QR/Code 39 использует официальный номер;
- существующие 372 предмета не потеряли данные;
- счётчики batch и publication сходятся;
- backup и restore-list завершаются успешно.

## 20. Порядок реализации

### Этап 0. Заморозка

1. Попросить 1С временно не отправлять новые выгрузки.
2. Получить исходный XML и вычислить SHA-256.
3. Зафиксировать текущие счётчики и backup.

### Этап 1. История импортов

1. Добавить batch и batch rows.
2. Добавить requestId/hash/membership.
3. Создать backfill текущего подтверждённого XML.
4. Проверить точное совпадение 10 617 GUID batch и текущей inbox projection.

### Этап 2. Анализ

1. Реализовать issues и классификацию.
2. Реализовать matching с 372 предметами.
3. Сформировать отчёт без изменения `items`.

### Этап 3. Интерфейс сверки

1. Добавить permission и admin routes.
2. Реализовать список batch, таблицу и diff.
3. Добавить решения и массовые действия.

### Этап 4. Публикация

1. Добавить external links и publication runs.
2. Реализовать dry-run и idempotent publisher.
3. Провести пилот 10–20 строк.
4. После приёмки публиковать оставшиеся подтверждённые строки порциями.

### Этап 5. Будущая синхронизация

1. Каждый POST создаёт новый immutable batch и обновляет inbox projection.
2. Автопубликация остаётся выключенной.
3. Администратор видит diff с последним опубликованным batch.
4. Автоматизацию отдельных безопасных полей разрешать только отдельным решением.

## 21. Критерии приёмки

1. Текущие 10 617 GUID представлены immutable batch с SHA-256 исходного XML.
2. Множество GUID исходного XML точно совпадает с текущей inbox projection.
3. Все строки имеют результат анализа и список проблем.
4. Существующие 372 предмета сопоставлены или явно оставлены без связи.
5. Ни один предмет не создан дважды при повторной публикации.
6. Ни один существующий кабинет, ответственный, фото или статус не изменён без подтверждения.
7. Нефизические ОС не попадают в основной каталог по умолчанию.
8. Четыре строки без инвентарного номера заблокированы.
9. Восемь строк со спорной стоимостью отмечены и не считаются финансово подтверждёнными.

## 22. Решения, которые должен подтвердить университет

Рекомендуемые значения уже указаны ниже; при отсутствии иного решения использовать их:

1. **Область:** публиковать только физические движимые ОС.
2. **Недвижимость/ПО/документы:** оставить в реестре 1С, не создавать как ТМЦ.
3. **Остаточная стоимость:** хранить отдельно от цены Inventory.
4. **Отрицательная стоимость:** блокировать до исправления бухгалтерией.
5. **Нулевая стоимость:** считать временно неподтверждённой для известных восьми GUID.
6. **Подразделение:** хранить отдельно, физическую комнату выбирать в Inventory.
7. **Ответственный:** не связывать автоматически по одному ФИО.
8. **Существующие 372:** сохранять их физические и операционные поля.
9. **Будущие выгрузки:** принимать в staging, не публиковать автоматически.
10. **Удаление/списание:** только через отдельное подтверждённое действие.
11. **Список 1С:** показывать `Снято с учёта` отдельно и только для чтения до сверки.
12. **Не в учёте:** не приравнивать к списанию без письменного правила бухгалтерии.
