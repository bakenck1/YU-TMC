# ТЗ: тестовый Dockflow API и учёт маркировки ТМЦ

> Статус: исходный тестовый этап завершён. Реальный `/api/v1` теперь читает
> профили сотрудников из Yessenov ID, а ТМЦ — из PostgreSQL. Этот документ
> сохраняет требования первоначального тестового этапа.

## 1. Цель

Создать тестовый API для интеграции с Dockflow. Внешняя система по ИИН
сотрудника получает его данные и список закреплённых за ним ТМЦ.

API доступен:

- локально для разработки;
- на тестовом сервере;
- через интерактивную Swagger-страницу `/api`.

На этом этапе API работает исключительно с изолированными фейковыми данными и
не читает реальные таблицы сотрудников и ТМЦ.

## 2. Swagger-документация

На `/api` размещается Swagger UI со следующими возможностями:

- название `Dockflow API`;
- ссылка на OpenAPI-спецификацию `/api/openapi.json`;
- кнопка **Authorize**;
- выполнение запросов через **Try it out**;
- описания параметров, кодов ошибок и примеры JSON-ответов;
- группы методов `Authentication`, `Employees`, `Inventory`.

Swagger и OpenAPI доступны без пользовательской cookie-сессии локально и на
тестовом сервере. Сами методы `/api/v1/*` требуют Bearer-ключ.

## 3. Тестовая авторизация

Для локальной среды и тестового сервера используется один общий тестовый ключ,
заданный переменной `DOCKFLOW_TEST_API_KEY`.

```http
Authorization: Bearer <TEST_API_KEY>
```

В Swagger через **Authorize** вводится только значение ключа: префикс `Bearer`
интерфейс добавляет автоматически.

Общий ключ действует только на тестовых данных. При подключении реальных ИИН,
телефонов и ТМЦ этот API отключается. Каждой реальной интеграции выдаётся
отдельный ключ, секрет хранится в виде хэша, а обращения записываются в журнал.

## 4. Методы первой версии API

| Метод | Назначение |
|---|---|
| `GET /api/v1/auth/check` | Проверка корректности API-ключа |
| `GET /api/v1/employees/{iin}` | Данные сотрудника и закреплённые за ним ТМЦ |
| `GET /api/v1/employees/{iin}/items` | Только список ТМЦ сотрудника |
| `GET /api/v1/employees` | Список тестовых сотрудников |
| `GET /api/v1/items` | Полный список тестовых ТМЦ |

Основной сценарий Dockflow:

```http
GET /api/v1/employees/990101123456
Authorization: Bearer <TEST_API_KEY>
```

```json
{
  "employee": {
    "iin": "990101123456",
    "fullName": "Тестовый сотрудник",
    "phone": "+77001234567",
    "login": "dockflow.test"
  },
  "items": [
    {
      "id": "00000000-0000-4000-8000-000000000001",
      "name": "Стул офисный",
      "barcode": "DF-000001",
      "inventoryNumber": "INV-2026-001",
      "quantity": 38,
      "status": "assigned",
      "storageLocation": "Корпус A, кабинет 205",
      "assignedAt": "2026-08-28T10:00:00Z",
      "cost": 45000,
      "markingType": "batch",
      "issueHistory": []
    }
  ]
}
```

Если ИИН не найден, API возвращает `404 Not Found`:

```json
{
  "error": "EMPLOYEE_NOT_FOUND",
  "message": "Пользователь с указанным ИИН не найден."
}
```

ИИН не из 12 цифр возвращает `400 INVALID_IIN`. Отсутствующий или неверный
ключ возвращает `401 UNAUTHORIZED`. Если ключ не настроен на сервере, API
закрывается с `503 API_NOT_CONFIGURED`. Все ответы API запрещены к кэшированию.

## 5. Тестовые данные

Создаются отдельные фейковые сотрудники с тестовыми ИИН, ФИО, телефонами и
логинами. На них оформляются только тестовые ТМЦ. Реальные персональные сведения
на этом этапе не используются.

Тестовая партия из 50 стульев показывает произвольное распределение: часть
закреплена за первым фейковым сотрудником, несколько штук — за вторым, а часть
остаётся на складе. Эти числа являются только фикстурой, а не правилом 7/3 или
другой фиксированной пропорцией. Полный список ТМЦ возвращает одну карточку
партии и массив `assignments`; endpoint сотрудника возвращает только
закреплённую за ним долю партии.

## 6. Правила учёта и штрихкодов

### Товар без штрихкода производителя

Система автоматически генерирует уникальный внутренний штрихкод и позволяет
распечатать наклейку.

### Одинаковые товары партией

Для партии одинаковых товаров создаются одна карточка и один штрихкод партии.
Остаток хранится количеством; отдельный штрихкод на каждую единицу не нужен.

### Несколько ответственных за части партии

Один документ выдачи может распределить любое целое положительное количество
между любым числом получателей. Никакой фиксированной пропорции нет: например,
из партии 50 штук можно выдать несколько штук другому сотруднику и оставить
остальное у текущего ответственного либо на складе. После проведения документа
сумма распределений не должна превышать количество партии, у каждого
ответственного фиксируется его количество, а свободный остаток пересчитывается.

В тестовом API это представлено одной карточкой с общим `quantity`, свободным
`availableQuantity` и массивом `assignments`. В ответе сотрудника `quantity`
означает количество, закреплённое именно за ним.

### Товары, на которые нельзя клеить этикетку

Для воды, бумаги, ручек, мышек, клавиатур, ковриков и подобных товаров штрихкод
размещается на коробке, упаковке либо на месте хранения. При поступлении
кладовщик выбирает один вариант маркировки:

1. `individual` — индивидуальный штрихкод;
2. `batch` — штрихкод партии;
3. `package_or_storage` — штрихкод упаковки или места хранения.

## 7. Реализованный следующий этап

Источником реальных ИИН, ФИО, телефонов, логинов, подразделений и должностей
утверждён защищённый endpoint `https://api.yu.edu.kz/api/v2/personnels/`. Сервер
аутентифицируется отдельным read-only service-токеном (`Authorization: Token`) из
`YESSENOV_DIRECTORY_API_TOKEN`; ключ, предъявляемый Dockflow, во внешний API не
передаётся.

Профиль считается доступным Dockflow только для активного `personnel` с валидным
12-значным `identify_code`. Закреплённые ТМЦ и их количества читаются из
PostgreSQL и связываются с профилем по ИИН. Recovery email, адреса, сведения о
документах, дата рождения, custom data и permissions наружу не выдаются.
